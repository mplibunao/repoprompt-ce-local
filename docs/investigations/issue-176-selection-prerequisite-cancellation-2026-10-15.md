# Investigation: MCP tools report an unready `read_file` selection as a cancellation (issue #176)

> Investigation report, observed 2026-10-15 on production build 53 (`main` at `ed18d09d`). It records what was true then. Where it disagrees with a current document, the current document is right.

## Summary
Issue #176's symptoms come from two independent defects, and both were reproduced live on production build 53.

1. **`Tool execution was cancelled.` within a second.** A `read_file` through a connection bound to a tab the window isn't showing leaves its mirror step `.invalidated` (`WorkspaceManagerViewModel.swift:6529–6537`). The coordinator records that outcome, and every later mirrored-selection drain on the same connection replays it at once. The guards turn it into a plain `CancellationError`. Upstream PR 1069 removes the cause, and upstream PRs 1049 and 1081 make the error typed. **#176's port should include 1069.**
2. **Context Builder answering from an empty selection.** The headless Claude Code provider ends a failed run as a success, so Context Builder commits the unchanged selection and sends the follow-up. Today every discovery run failed with `401 token expired or incorrect` and still returned a normal answer. The 401 came from the GLM endpoint that the `claudeCodeGLM` provider uses, which runs Claude Code against a non-Anthropic GLM model. Upstream has the same defect, so this needs its own bugfix issue.

3. **Context Builder discovery starved by a busy window.** A discovery `read_file` that times out after 30 s leaves a stuck structure provider. After that, every read in the window fails with `tool_execution_structure_settlement_busy`, so discovery ends with almost nothing selected, and defect 2 still reports success. A Codex discovery run reproduced this in the owner's window at 10:00 UTC today, and the window stayed wedged afterwards.

A further factor makes the first defect frequent. Claude Code Desktop runs one RepoPrompt MCP proxy process for all its Code sessions, so they share one tab binding. One session's `bind_context` moves the others, and a session's reads then auto-select into another session's tab.

## Scope
Issue #176 asks to port upstream PRs 1049 and 1081, which replace the plain `CancellationError` thrown by eight MCP tools after a deferred or invalidated `read_file` auto-selection wait with a typed error. This investigation answers three questions:

1. **20 ms cancellation cause.** On 2026-10-14, production build 50 (`local/v1.4.0-b50`), two `context_builder` calls from a Claude Code session failed with `Tool execution was cancelled.` about 20 ms after they were sent, although the wait in `drainReadFileAutoSelection` can run up to 10 seconds. Does the guard explain it, and why did the wait end so fast?
2. **Empty Context Builder selections.** On 2026-10-14, production build 51 (`local/v1.4.0-b51`), several `context_builder` calls with `response_type: plan` finished normally with a 0-token selection. Do the guard (in the discovery agent's own `manage_selection` call), the `tool_execution_structure_settlement_busy` error, or concurrent Context Builder runs in one window (#143) explain them?
3. **Port scope and drift.** What does porting upstream PRs 1049 and 1081 onto the distribution's `main` involve: divergence, conflicts, tests, and any later upstream follow-ups?

## Symptoms
- Build 50, 2026-10-14: two `context_builder` calls failed with `Tool execution was cancelled.` about 20 ms after being sent. The session had run `read_file` on the same connection earlier. `manage_selection op=get` still worked. The same request through `rpce-cli` on a fresh connection with no earlier read ran normally.
- Build 51, 2026-10-14 around 04:10 UTC, five-root workspace, several agent sessions in one window: two `context_builder` plan calls in different tabs, about two minutes apart, both finished discovery with a 0-token selection and returned a normal result. A third call routed by window only ran discovery for 108 s and also returned a 0-token result. Neither connection had run `read_file` first.
- Same window, minutes later: `read_file` and `get_code_structure` failed with `tool_execution_structure_settlement_busy` ("reached its limit of one released cancellation-ignoring structure provider"). Hours later, reads worked again without a restart.
- Two later calls in a new tab failed with `Context Builder response delivery did not finish` (filed as #182). After an app restart the same request selected 17 files, with about 22 minutes of discovery.
- The discovery agents' sessions don't appear in `history` or `agent_manage list_sessions`, so their tool calls aren't recorded.

## Hypotheses
- **H1.** The `context_builder` guard (`MCPContextBuilderToolProvider.swift` 453–456) threw `CancellationError` because `drainReadFileAutoSelection` returned deferred or invalidated, not completed. The 20 ms duration means the wait returned on a fast path, not on its 10-second timeout.
- **H2.** A Context Builder discovery agent that ran `read_file` and then `manage_selection` hit the `manage_selection` guard (`MCPSelectionToolProvider.swift` 187), got `Tool execution was cancelled.`, and stopped without selecting anything. Context Builder then sent the follow-up with an empty selection, because nothing checks for one outside review targets.
- **H3.** The structure-settlement capacity limit (`MCPDomainCodeStructureSettlementRegistry.swift`) made the discovery agent's file and structure reads fail, so it selected nothing. This is independent of the guard.
- **H4.** Concurrent Context Builder runs in one window (#143) interfere through shared tab or selection state.
- **H5.** Upstream PR 1003 (upstream issue 1002), a lock re-entry deadlock in the worktree publication permit path, produces the same busy error. Recovery without a restart argues against a permanent deadlock.

## Investigator Findings: drain outcomes, fast cancellation, and port map (questions 1 and 3)

Paths are distribution `main` (`ed18d09d`) unless marked upstream. Terms used below:
- **Key**: the `ContextKey` that auto-selection work is filed under: window, workspace, tab, connection, run ID, and binding generation (`MCPReadFileAutoSelectionCoordinator.swift:31–41`). The binding generation is a counter assigned on every bind (`MCPServerViewModel+TabContext.swift:659–662`).
- **Canonical apply**: writing the read file into the tab's stored selection.
- **Mirror**: copying a tab's stored selection into the window's visible file list. A tab's mirror requests are numbered by ticket, and each ticket ends converged, deferred, invalidated, or cancelled.
- **Mirrored drain**: a drain with the `.mirroredSelectionAndMetrics` requirement, which waits for canonical apply and the mirror. **Canonical drain**: `.canonicalSelection`, which waits for canonical apply only. `context_builder`, `ask_oracle`, `oracle_send`, `workspace_context`, prompt export, and `manage_selection` mutations drain mirrored. `get_code_structure` without paths, `get_file_tree mode=selected`, and `manage_selection op=get` drain canonical.

### Q1(c) Binding keys, binding changes, and pending auto-selection work
**How a binding is keyed.** Bindings are stored as `tabContextByConnectionID: [UUID: TabContextSnapshot]` (`MCPServerViewModel.swift:2228`). The app creates that UUID for each accepted bootstrap socket (`MCPConnectionManager.swift:4641`). The stdio proxy `repoprompt_ce_cli` opens one bootstrap socket per process, identified by a session token that lasts the process's lifetime (`Sources/RepoPromptMCP/main.swift:2046–2051`). Client name isn't part of the key. The app uses it for window-affinity reuse (`MCPConnectionManager.swift:2720–2736`), for persisted routing records (window affinity, not tab), and for queued run-scoped contexts, which a connection can take only with an exact run-ID hint (`MCPServerViewModel+TabContext.swift:3470–3478`). Client version isn't used. Two MCP clients therefore share a binding exactly when they share one proxy process.

**Which it is today.** A process listing at 2026-10-15 09:13 UTC shows Claude Desktop (PID `<desktop>`) hosting one `repoprompt_ce_cli` (PID `<desktop CLI>`, through its `disclaimer` helper) beside its other hosted MCP servers. Its 14 Code session processes (`claude --output-format stream-json`) have no RepoPrompt MCP child. Each RepoPrompt Agent Mode run (`claude -p … --mcp-config <RepoPrompt CE profile>`) and each terminal `claude` has its own `repoprompt_ce_cli`. Desktop routes every Code session's RepoPrompt calls through one connection, and the app has no identity that tells those sessions apart.

**Unbound after a Desktop timeout.** A proxy reconnect opens a new socket, so the connection gets a new UUID (4641) and starts unbound. **What a binding change does to pending work.** Work is filed under the key resolved from the binding at read time (`MCPServerViewModel.swift:4980–4994, 5264–5281`). Every `bindTabForConnection`, including a rebind to the same tab, releases the old binding and assigns a new generation (`MCPServerViewModel+TabContext.swift:1202–1207`). Releasing invalidates the old key (686–694 → coordinator 761–771): a parked waiter returns `.invalidated`, and a batch not yet applied is skipped (881, 889, 908). The drain builds its key from the binding at drain time (`MCPServerViewModel.swift:5010–5014`), so after a rebind the drain has no work to wait for and returns `.completed` (670–671). A binding change produces at most one `.invalidated`, for a drain parked at that moment, and it clears a failing key rather than creating one.

**Why the mirrored drain fails within milliseconds and keeps failing** (the Phase 3 questions):
1. A read files work under key K and writes into K's tab T. The canonical apply changes T's stored selection and requests mirror ticket t (coordinator 912–916, 986; `MCPServerViewModel.swift:5502`).
2. The mirror runs right away. It checks the window, not the binding: is T the active compose tab of the window's active workspace (`WorkspaceManagerViewModel.swift:6533–6536`)? If not, ticket t ends `.invalidated`. If T is visible, the window's single mirror worker applies it, and a competing request can end t `.deferred` (`WorkspaceSelectionCoordinator.swift:1071–1081`, 1091–1118).
3. `completeMirrorBatch` records that result for ticket t (1196–1214). Pruning keeps the record because K's canonical lane still names t as its required ticket (1265–1285). Lanes stay until K is invalidated or retired (1564–1597), and a drain that doesn't complete leaves them in place.
4. Every later mirrored drain under K finds canonical work complete, finds the mirror past t (1339), and returns the recorded result (1255–1263) without registering a waiter, so the 10 s deadline (1365–1372) never starts. A canonical drain stops after canonical work and returns `.completed`, and `manage_selection op=get` keeps working.
5. Only two things clear K: a later mirror on T that converges past t (1261), which needs another selection-changing read into T while T is visible, or a new key from a rebind or reconnect. Switching to T in the UI doesn't clear it.

So the failure needs the read and the drain to use the same key, and T to be a tab the window wasn't showing, or a mirror that was displaced. A shared Desktop binding makes that common, because reads land in another session's tab, which is usually not the visible one. A binding change between read and drain doesn't cause it. Upstream PR 1069 changes step 2: a background tab updates its presentation and ends `.converged` (see Q3).

## Root Cause

### 1. Fast, repeating `Tool execution was cancelled.` (questions 1 and 3)
1. A `read_file` or eligible `file_search` on an MCP connection auto-selects the file into the connection's bound tab T and queues a mirror of T's selection into the window's visible file list.
2. On `main`, the mirror returns `.invalidated` immediately when T isn't the active compose tab of the window's active workspace (`WorkspaceManagerViewModel.swift:6529–6537`, called from `MCPServerViewModel.swift:2222–2223`). MCP and agent tabs are background tabs by default, so this is the common case.
3. `MCPReadFileAutoSelectionCoordinator.completeMirrorBatch` records the outcome for that ticket (1189–1234), and pruning keeps it while the canonical lane references the ticket (1265–1285).
4. Every later drain with the `.mirroredSelectionAndMetrics` requirement on the same key finds the ticket settled and replays the recorded outcome without waiting (1255–1263, 1330–1341). The 10 s deadline never starts.
5. The eight guards throw `CancellationError` for any outcome but `.completed`. Examples are `MCPContextBuilderToolProvider.swift:453–458` and `MCPSelectionToolProvider.swift:187–189`, and the full list is in pair 1's port map. `runTool` maps that to `MCPToolExecutionCancelledError`, "Tool execution was cancelled." (`MCPServerViewModel.swift:4171–4173`).
6. Drains with the `.canonicalSelection` requirement stop before the mirror check, so `manage_selection op=get` keeps working. That is the pattern in the issue body, in session A, and in the live reproduction.
7. The failure clears only when a later mirror of T converges past the ticket, or when the connection's binding changes. A same-tab `bind_context` that reports `Changed: no` doesn't clear it.

Contributing factor: a host that runs one `repoprompt_ce_cli` proxy for several sessions gives them one binding, because the app keys bindings per socket (`MCPConnectionManager.swift:4641`; `MCPServerViewModel.swift:2228`). Claude Code Desktop does this for all its Code sessions. Sessions on one proxy share one binding, so one session's `bind_context` moves the others, and reads land in tabs the reader didn't choose, usually background tabs. This was observed live. Its role on 2026-10-13 and 2026-10-14 is unverified, and session B's selection contents argue against it there.

### 2. Context Builder completes with an empty or unchanged selection (question 2)
1. Discovery for the Claude-compatible providers runs `ClaudeCodeAgentProvider` (`AgentRuntimeProviderService.swift:247–270`). Its `result` case (`ClaudeCodeAgentProvider.swift:262–290`) never reads `is_error`, `subtype`, or `errors`. Nothing reads `isApiErrorMessage`. Once `message_stop` arrives, the loop breaks before reading the exit status and finishes the stream with "Treating as success" (457–467, 499–515).
2. `consumeContextBuilderProviderStream` returns `.completed` whenever the stream ends without throwing (`ContextBuilderAgentViewModel.swift:3494–3504`). The run then commits its frozen tab context without comparing it with the starting state (3169–3176; `MCPServerViewModel+TabContext.swift:4572`).
3. `responseDisposition` returns `.generate` for a completed run (`MCPContextBuilderToolProvider.swift:996`), and nothing outside review mode checks for an empty selection before the follow-up (`ContextBuilderReviewTarget.swift:256, 559` cover reviews only).

Today's trigger was an expired GLM token for the `claudeCodeGLM` discovery provider. Every discovery request got `401 token expired or incorrect`, and the run made no tool calls and ended in a synthetic error message, yet the caller got a normal answer. Session C's build 51 runs on 2026-10-14 reported a genuinely empty selection. They followed the same completed-without-progress path, but which provider ran them and why it selected nothing is unverified, because no discovery transcript exists for them.

### 3. Structure-settlement busy errors starve discovery (H3, confirmed)
A Context Builder re-run at 09:59 UTC with Codex discovery, after the Context Builder agent was switched away from GLM, ran 223 s and finished as "run complete" with two files selected. Its Codex session log in the production profile shows the sequence:
1. 09:59:55: `read_file` of `repoprompt-ce/CLAUDE.md` returned `tool_execution_timeout: Tool 'read_file' exceeded its 30-second execution …` after 35 s, and again at 10:01:05.
2. From 10:00:39 on, `read_file`, `get_file_tree`, and `prompt set` returned `tool_execution_structure_settlement_busy`, first as "A prior timed-out MCP operation for window N …" and then as "Window N reached its limit of one released cancellation-ignoring structure provider."
3. Two `manage_selection add` calls succeeded, taking about 13 s each, for the coordinator file and this report. They were the only selection.
4. The handoff `prompt set`, whose text began "Resume context discovery before answering; this handoff is incomplete", was itself rejected as busy. The follow-up never saw that warning.
5. At 10:06 UTC a one-line `read_file` from a fresh `rpce-cli -w 1` connection still failed at once with the same busy error. The window stays wedged until the stuck provider settles or the app restarts.

The mechanism matches the explore agent's description of the registry under "Upstream PR 1003": a provider that outlives watchdog cancellation keeps its lease, and with `releasedProviderLimit = 1` the next structure-backed call is refused. Why a read of `CLAUDE.md` stalled for 30 s in this window is not established. Upstream PR 1003's lock re-entry fix is one candidate. The window then held about 1,170 tabs and several concurrent agent sessions. This defect combines with defect 2: discovery can't read, makes few or no selections, and the run still counts as completed. It is the strongest explanation for session C's empty build 51 runs, because the issue comments report busy errors in the same window around 04:00–04:13 UTC on 2026-10-14. No discovery transcript exists to confirm it.

### Eliminated hypotheses
- **H2, the discovery agent's own `manage_selection` hitting the guard:** none of the 37 discovery transcripts from 2026-10-13 to 2026-10-15 contains `Tool execution was cancelled.`
- **H4, concurrent per-tab Context Builder runs:** each run commits only its own frozen context, and a commit against another run's context fails the run (`MCPServerViewModel+TabContext.swift:4603, 4713`).
- **Stale accounting for build 51's 0 tokens:** the formatter prints `Total tokens: 0` with no Files line only for an empty selection (`ToolOutputFormatter.swift:3351–3372`). Today's `0 tokens` is a per-file line under `Total tokens: pending`.
- **A binding change between read and drain as the repeating cause:** it yields at most one `.invalidated` for a parked waiter, then the new key completes.
- **Tab claim, ownership loss, window or tab close, the 10 s mirror deadline, and client-side cancellation:** each is ruled out by pair 1's Q1(b) and Q1(d).

## Preventive Measures
- The typed errors from the port make a stuck prerequisite visible as `selection_prerequisite_deferred` or `selection_prerequisite_invalidated` instead of a cancellation. Production logs recorded none of these events, so the error text is the only field signal.
- A provider-stream test where a `result` with `is_error: true`, or an `isApiErrorMessage` assistant message, makes the discovery stream fail would catch a regression of defect 2 at the lowest layer.
- Agent workflows that drive RepoPrompt from Claude Code Desktop should not assume a private binding. They should re-check `bind_context status` before selection-sensitive calls, or route through `rpce-cli`.
