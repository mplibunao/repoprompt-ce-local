## 2. Disagreements with a user-visible effect

Two interleavings were found where authorities answer differently and the difference reaches the MCP caller. Everything else in the table was traced to the same observable answer on every ordering I could construct without reading `AgentRunSessionStore`'s wait semantics.

### D1. Provider change while an MCP start is queued: prompt dropped, `poll` says failed, `wait` runs to its timeout

Ticket says *superseded, nothing to settle*; the barrier and store are never told; the live snapshot synthesizes *failed*.

1. `agent_run start` on a Codex session: activation raises the flag (VM B:9253); `submitUserTurn` installs ticket T (B:15940), appends the optimistic prompt (B:16441-16450), resets `runState` to `.idle` (B:16328-16331), and queues the dispatch task at the Codex gate (B:16501-16541).
2. Before the gate turn, the tab's provider changes — the picker `didSet` (VM B:299-317) or an MCP reconfiguration through `mcpConfigureSession` with a different agent (B:8880-8884). Both call `invalidatePendingStartup(.superseded)` (TS B:942-957): T resolves `.superseded`, its gate ticket is cancelled, and the flag is cleared (same activation generation).
3. The dispatch task resumes with `gateTurnGranted == false` → `sendOutcome = .cancelled` (B:16558-16559). `resolveStartupTicketAfterRunServiceReturn` (B:16593) is a no-op because T is already resolved (TK:184-188). `startAgentRun` was never entered, so neither `settleStartRejectedBeforeProvider` nor the barrier runs; the optimistic prompt is removed (B:16623-16628) and no error item is appended.
4. Observable state: `runState == .idle`, no unresolved ticket, flag false, no user item. `poll` falls through `mcpLiveStatusResolution` to idle-without-evidence and returns `failed` with "No terminal result was recorded…" (B:6605-6610). `wait` on the session's epoch never receives a publication — only VM B:5945 and B:6367 publish, and neither runs — and blocks until its own timeout. The instruction is gone from the transcript.

On `origin/main` the same action let the queued task start the run under the new provider: a different failure, but not a lost prompt plus a hanging `wait`. Reachability: a deliberate provider change on the child's tab while it is queued, not the concurrent-start race this branch fixes.

### D2. Layer-1 FIFO follower: `poll` reports `failed` for a session that is about to run the follower

The session-wide flag is cleared on the head's behalf while the follower it was also raised for is still queued.

1. Head start H is queued with ticket T_H. An MCP steer arrives while the session is inactive: `executeSteer` raises the flag (MT:1068) and dispatches; `submitUserTurn` sees T_H unresolved, so the steer becomes follower F with no ticket of its own, registered on T_H (VM B:15940, 16502-16507, 16669).
2. H reaches the runner; readiness fails; the runner commits `.failed` through the barrier (RN B:85-93 → CO B:6655-6686). `startAgentRun`'s `defer` runs `clearPendingStartFlagIfOwned` (VM B:18007-18031): T_H is still unresolved and current, so the flag — raised for H *and* F — is cleared.
3. Back in H's dispatch task, `resolveStartupTicketAfterRunServiceReturn(.rejected)` runs (B:16593), then H's `defer` finishes its gate ticket, which resumes F's continuation on a later MainActor hop (TS B:358, B:382).
4. In that hop: no unresolved ticket, `runState == .failed`, flag false. A `poll` returns `failed` with H's error text (B:6597-6604 not taken; B:6605-6607 settled; B:6618 mask absent). When F's hop runs, `promoteQueuedCodexSubmissionToStartup` installs T_F and resets `runState` to `.idle` (B:16287-16331), and the next `poll` reads `running` again.

Window: one MainActor hop between H's gate `finish` and F's promotion, so an orchestrator polling on an interval is unlikely to observe it, and `wait` is unaffected because F's epoch differs from H's. The trigger — a steer during a queued start — is the issue #73 case layer 2 rejects, so this disappears when layer 2 lands.

## 3. Verdict

Safe to merge as a scoped fix. The branch adds the ticket beside the existing flag rather than replacing anything, the barrier remains the only path that settles a start rejected by a runner or cancelled through `cancelRun`, and the two disagreements above sit outside the concurrent-start race: D1 needs a deliberate provider change on a queued child's tab and deserves its own tracked issue, and D2 is a one-hop `poll` flicker that layer 2 removes. The review churn the owner observed is the price of the added authority, not a sign the fix is incomplete: every new checkpoint has to agree with the flag, the run-ID lifecycle, and the ownership binding separately, which is exactly where the interleaving findings clustered.
