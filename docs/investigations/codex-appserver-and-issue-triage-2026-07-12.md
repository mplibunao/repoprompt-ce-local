### Codex protocol ground truth (explore agent, 2026-07-12) — challenges upstream issue 449's mechanism
- codex-rs source at `rust-v0.144.1` (`codex-rs/app-server-protocol/src/protocol/v2/turn.rs#L285-L295`): `UserInput::Text { text, #[serde(default)] text_elements }` with `#[serde(tag = "type", rename_all = "camelCase")]`. `rename_all` affects only variant names; the field is snake_case `text_elements`, no alias, **no `deny_unknown_fields`**. Same shape at `rust-v0.120.0`; no revision in between ever accepted camelCase.
- Consequence per serde semantics: an input item containing `"textElements": []` plus a valid `"type"`/`"text"` should be **accepted with the unknown key silently ignored** and `text_elements` defaulted to `[]` — i.e., for CE's always-empty array, byte-for-byte harmless.
- Reconciliation with the 2026-07-08 probe doc (`repo-prompt-codex-agent-hang-2026-07-08.md`): that probe's camelCase rejection error was `Invalid request: missing field type` — a missing **tag** complaint, suggesting the probe payload was structurally malformed beyond the key casing. Real CE payloads do include `"type": "text"` (asserted by upstream PR 450's own tests).
- Open question this raises: the `textElements`→`text_elements` rename may be protocol-hygiene-correct but **not the actual cause** of the upstream issue 449 hang; candidate true causes: the Codex startup-stall class (upstream `1ab555e6`, not in the builds that exhibited hangs) and/or terminal-event drops (`codex/event/task_complete` explicitly ignored at `CodexNativeSessionController.swift:2438`, no `turn/start` timeout at `:1317`, per the 07-08 doc).
- Deciding experiment dispatched: live `codex app-server` (0.144.1) probe sending the exact unpatched CE item shape (`type`+`text`+`textElements`) vs patched (`text_elements`) — completed/rejected/hung per variant.

### Deciding experiment RESULT (live codex app-server 0.144.1 probe, 2026-07-12)
- **Variant A (`textElements`, unpatched CE shape): HUNG.** The turn ran, the model streamed `OK`, `item/completed` and `thread/status idle` arrived — but **no `turn/completed` (or error) was ever emitted** within the 90 s timebox. Codex even normalized the echoed user item to `text_elements: []` internally, yet still omitted the terminal turn notification.
- **Variant B (`text_elements`, patched shape): COMPLETED** — identical flow plus `turn/completed` (status `completed`, durationMs 3372).
- Verdict: **the serde ground-truth reasoning above is refuted empirically.** The unknown camelCase key is *not* harmless: it suppresses the terminal `turn/completed` event on codex-cli 0.144.1 while letting the turn otherwise run. Since CE resolves a turn only on the terminal event, this exactly reproduces the upstream issue 449 indefinite "Thinking…" hang. **Upstream issue 449 is VALID and upstream PR 450 is the correct, still-needed fix** (upstream main also still carries the bug).
- Mechanism note: rejection-vs-ignore at the serde layer was the wrong frame — the failure is downstream in codex's turn bookkeeping, not input deserialization.

## Investigator Findings

### Q1 — MCP bridge teardown crash

1. **The crashing async frame is the retry-backoff sleep inside the transport child, not an escaping TaskGroup child.** `MCPService.run()` creates a throwing task group and its third child calls `runTransport()` (`Sources/RepoPromptMCP/main.swift:2113-2135`). When any child completes or throws, `run()` cancels the group (`:2140-2153`). `runTransport()` can then be suspended in its transient-failure backoff at `Task.sleep` (`:2263-2320`). For the installed 1.0.27 binary in the 2026-07-11 crash report, image-base/offset mapping placed the reported `MCPService.runTransport()+44` return PC immediately after `_swift_task_dealloc`; `nm` and `otool` placed the matching allocation/resume continuation around `ContinuousClock.sleep`. This proves the abort occurs while the compiler-generated sleep frame is being deallocated on resume, plausibly when group cancellation interrupts the backoff. The source does not let a TaskGroup child escape: the group scope remains structured and waits for its children. The best-supported diagnosis is therefore a Swift compiler/runtime async-frame LIFO violation exposed by this cancellation/error-control-flow shape, rather than an ordinary escaped-child bug. **Confidence: high on the crash site; medium-high on cancellation as the trigger and compiler/runtime code generation as the underlying mechanism.**

2. **The kill-signal continuation is a separate lifecycle hazard, but it does not match this crash stack.** `waitForKillSignal()` stores a checked continuation and its synchronous cancellation handler launches an unstructured `Task` to resume it on the actor (`Sources/RepoPromptMCP/main.swift:2063-2093`); teardown can clear the stored continuation without resuming it (`:2095-2100`). That construct deserves hardening, but it belongs to the first task-group child, while all 28 reports identify `closure #3` / `runTransport()`. **Confidence: high that this is not the primary crash site; medium that it is an independently actionable cleanup risk.**

3. **The crash remains live upstream.** The path-scoped `HEAD..origin/main` log for `Sources/RepoPromptMCP/main.swift` and `Sources/RepoPromptShared/MCP` contains only release-version bumps (`76e1de11`, `50c3dcda`, `59496eab`) plus `96e039a6`'s CLI-path repair. `git diff HEAD..origin/main -- Sources/RepoPromptMCP/main.swift` changes only `CLI_VERSION` from 1.0.24 to 1.0.27; none of `run()`, `runTransport()`, the retry sleep, or the kill-signal continuation changes. The five reports from the later 1.0.27 binary are consistent with that result. **Confidence: high.**

### Q2 — Child-agent MCP tool provisioning

1. **Codex children are intended to receive RepoPrompt MCP tools under `mcp__RepoPromptCE__<tool>`.** The server name is the fixed source literal `RepoPromptCE`, and the configuration defaults to the flavor-specific stable CLI helper (`Sources/RepoPrompt/Infrastructure/MCP/RepoPromptMCPServerConfiguration.swift:16-26`). Start/resume calls `ensureCodexServerForDiscovery()`, registers expected MCP ownership, starts app-server, then supplies runtime overrides (`Sources/RepoPrompt/Infrastructure/AI/Providers/Codex/AppServer/CodexNativeSessionController.swift:1060-1092`). The Codex config parser/installer owns `[mcp_servers.RepoPromptCE]` (`Sources/RepoPrompt/Infrastructure/AI/Providers/Codex/CodexIntegrationConfiguration.swift:131-168,1077-1088`), and prompt rendering qualifies canonical tools with `mcp__RepoPromptCE__` (`Sources/RepoPrompt/Infrastructure/AI/Prompts/AgentModePrompts.swift:354-371`). The Codex capability policy grants agent-session control, and the explore advertisement policy explicitly keeps `set_status` visible (`Sources/RepoPrompt/Infrastructure/MCP/Policies/AgentModeMCPToolPolicy.swift:39-50`; `Sources/RepoPrompt/Infrastructure/MCP/Policies/AgentModeMCPToolAdvertisementPolicy.swift:17-38,51-84`). An explore child with a healthy route should therefore see `mcp__RepoPromptCE__set_status`. **Confidence: high.**

2. **The prefix is not build-variant-dependent.** `RepoPromptCE` is not derived from `CFBundleName`, bundle ID, or the on-disk app name. Debug versus release changes the helper/routing identity—`repoprompt_ce_cli_debug` versus `repoprompt_ce_cli` and corresponding filesystem configuration—not the MCP namespace (`Sources/RepoPrompt/Infrastructure/Process/CLI/CLISymlinkManager.swift:14-34`; `Sources/RepoPromptShared/MCP/MCPFilesystemIdentity.swift:79-112`). Coexisting `RepoPrompt.app` and `RepoPrompt CE.app` can still route through different helper instances, but both advertise the same `mcp__RepoPromptCE__` prefix. **Confidence: high.**

3. **The most plausible failure is missing per-child MCP routing, not a naming or role-policy mismatch.** Each child receives a fresh app-server client/controller (`Sources/RepoPrompt/Features/AgentMode/ViewModels/AgentModeViewModel.swift:1425-1451`). The coordinator can establish a live Codex thread and then ignore a false result from the MCP routing wait (`Sources/RepoPrompt/Features/AgentMode/Runtime/Codex/CodexAgentModeCoordinator.swift:3871-3917`); `releaseWhenRouted()` explicitly returns false and clears pending policy after timeout/failure (`Sources/RepoPrompt/Infrastructure/MCP/MCPBootstrapLease.swift:238-275`). `startOrResume()` also discards the success Boolean from `ensureCodexServerForDiscovery()` (`CodexNativeSessionController.swift:1074-1088`). Either transient route/bootstrap failure can leave a functioning Codex child with native shell tools but without RepoPrompt tools. The sibling children only demonstrated that shell remained usable; because they never invoked RepoPrompt MCP, they do not prove that their MCP tools were present. If they also lacked MCP, only the instruction-sensitive child surfaced the shared outage; if they had MCP, the route failure was isolated to one child. **Confidence: medium-high on routing/bootstrap failure as the mechanism; high that sibling shell success does not establish MCP availability.**

### Q3 — App-server idle death and restart stalls

1. **CE intentionally retires each idle per-tab Codex app-server after five minutes.** The coordinator defaults and clamps the idle delay to 300 seconds (`Sources/RepoPrompt/Features/AgentMode/Runtime/Codex/CodexAgentModeCoordinator.swift:328-360`). Terminal commit schedules idle shutdown (`:5345-5391`); the timer rechecks that the tab is inactive, records reconnect metadata, and calls `shutdownCodexSession()` (`:7144-7184`). Shutdown stops the controller/client and clears the stored controller and event state (`:8159-8201`; `Sources/RepoPrompt/Infrastructure/AI/Providers/Codex/AppServer/CodexNativeSessionController.swift:1716-1746`). The 75-minute gap therefore does not establish that the child exited spontaneously or that its death was first discovered by the next request. The next turn should create a replacement controller/process and resume the saved thread; the observed `Codex native resume failed: Codex app-server process is not running` is better classified as replacement startup/resume failure. **Confidence: high.**

2. **Other stop paths exist, but no searched idle-independent memory-pressure policy does.** Provider switching shuts the controller down (`CodexAgentModeCoordinator.swift:2640-2669`); clearing/cancelling a session and tab lifecycle cleanup also stop it (`:7987-8024,8088-8157`). The app-server client additionally invalidates a process that fails its liveness probe, handles stdout EOF as transport termination, and poisons timed-out `thread/start` or `thread/resume` transports (`Sources/RepoPrompt/Infrastructure/AI/Providers/Codex/AppServer/CodexAppServerClient.swift:288-294,465-505,970-1057`). No memory-pressure, thermal, or unrelated long-idle kill hook was found in the client, controller, or coordinator. **Confidence: high.**

3. **Existing exit diagnostics are insufficient to determine why an unexpected child exited.** Agent Mode constructs the client with debug logging off by default (`CodexAppServerClient.swift:134-157`; `AgentModeViewModel.swift:1425-1451`). Stderr is drained but only printed when debug logging is enabled, and no stderr tail is retained (`CodexAppServerClient.swift:1009-1037`). `lastTransportTerminationReason` is stored (`:297-320,544-553`) but exposed only through DEBUG test support, while `ProcessTermination.terminateAndReap` returns an exit result that the client discards (`:680-698`). Thus current code has neither a durable child stderr tail nor an original exit-status record for this incident. **Confidence: high.**

4. **Upstream `1ab555e6` plausibly explains the repeated replacement-start failures on this fish-based machine, but it does not explain the expected idle retirement.** Before the commit, environment capture invokes the user's login shell interactively with `-l -i -c env`, and executable resolution queries the interactive shell before PATH; fish's interactive startup/config is therefore on the critical launch path. `1ab555e6` makes Codex app-server/preflight use non-interactive login-shell capture, resolves Codex from PATH before shell fallback, and changes the optional post-start memory-mode disable from a potentially 120-second blocking request into two bounded one-second attempts plus a background retry. The affected debug build predates that commit, and the commit explicitly targets Codex startup stalls, so it fits the 23-minute period in which fresh controllers could not become ready. Without retained stderr/exit diagnostics, the exact submechanism—interactive fish startup/path lookup versus the optional memory-mode request—cannot be proven retrospectively. **Confidence: medium-high that the commit is applicable; medium on exact incident attribution.**

## Root Cause

**1. Upstream issue 449 / upstream PR 450 (Codex "Thinking…" hang) — CONFIRMED, protocol-level.** CE's turn dispatch sent `"textElements"` (camelCase) in the text input item (`CodexNativeSessionController.swift:1629` on `origin/main`; fixed on this branch). Live probe against `codex app-server` 0.144.1: with `textElements` the turn runs and the model responds, but **`turn/completed` is never emitted**; with `text_elements` it completes normally. CE resolves turns on the terminal event → indefinite hang. The defect shipped in the initial CE snapshot (`351e9803`), which explains why the maintainer (on Classic) never saw it and why the reporter only hit it after moving to CE. The serde-only analysis (unknown field ignored ⇒ harmless) was refuted empirically — the failure is in codex's turn bookkeeping, not input deserialization.

**2. Previous agent's app-server failure — replacement-startup stall on a pre-`1ab555e6` build, not an idle death.** CE retires idle per-tab app-servers after 300 s by design (`CodexAgentModeCoordinator.swift:339`, verified). After the 75-minute gap the next turn must spawn a replacement; on the debug build (54 commits behind) that startup path contains three hazards all fixed by upstream `1ab555e6`: interactive fish login-shell environment capture (`fish -l -i -c env`), interactive-shell-first codex executable resolution, and a synchronous `thread/memoryMode/set` call with a ~120 s timeout that can fail an otherwise-successful start. Fresh sessions kept failing because every new controller re-enters the same deterministic environment path — no poisoned global state (each controller gets a fresh client; verified per-client `startupTask`/generation fencing). Codex CLI version is **not** the cause (0.144.1 is latest). Exact submechanism is unprovable retrospectively because the build retains neither child stderr nor exit status.

**3. MCP bridge instability (`Connection closed`, tool timeouts) — live crash in `repoprompt-mcp` teardown.** 28 SIGABRT reports share one signature: `swift_task_dealloc` under `MCPService.runTransport()`; symbol mapping places the abort at deallocation of the retry-backoff `Task.sleep` frame (`Sources/RepoPromptMCP/main.swift:2316`, verified) when group cancellation interrupts the backoff (`run()` cancels the group at `:2140-2153`). Structured concurrency is not visibly violated in source — best-supported diagnosis is a compiler/runtime async-frame teardown issue exposed by this cancellation shape. **Unfixed on `origin/main`** (only `CLI_VERSION` bumps touch the file). It struck this investigation twice (pair attempt 1 wedged; three `read_file` timeouts during verification).

**4. Child-agent MCP tool gaps — silent per-child routing/bootstrap failure.** Children should get tools under the fixed, build-independent prefix `mcp__RepoPromptCE__*` (`RepoPromptMCPServerConfiguration.swift:16`, verified literal). But the coordinator ignores a false MCP-routing-wait result (`CodexAgentModeCoordinator.swift:3871-3917`), `releaseWhenRouted()` returns false and clears policy on timeout (`MCPBootstrapLease.swift:238-275`), and `startOrResume()` discards `ensureCodexServerForDiscovery()`'s success flag (`CodexNativeSessionController.swift:1074-1088`) — so a child can start with shell tools but no RepoPrompt tools, with no surfaced error. Combined with the stop-don't-substitute agent instruction, this yields hard refusals that look like agent flakiness.

## Eliminated hypotheses
- **"Codex CLI is outdated" (maintainer's question)** — 0.144.1 is the latest stable; the hang reproduces on it.
- **camelCase key is harmless per serde** — empirically refuted (see deciding experiment).
- **App-server died spontaneously after ~75 min idle** — idle retirement at 5 min is intentional; the failure was in replacement startup.
- **Poisoned global app-server state blocking fresh sessions** — clients are per-controller; generation fencing verified; shared inputs (env capture, resolution) explain the repetition instead.
- **MCP tool prefix differs between debug and release builds** — server name is a fixed source literal; debug/release differ only in helper/socket identity.
- **Upstream PR 472 superseded by the upstream update** — no upstream commit touches the selection-mirror coordinators.

## Preventive Measures
- Keep the local checkout within a few commits of `origin/main` when the debug build hosts real agent work; being 54 commits behind meant running with known-fixed startup stalls.
- Before attributing agent failures to one defect, separate the failure classes (turn hang vs spawn failure vs bridge crash vs tool provisioning) — this incident conflated four distinct defects into "agents are inconsistent."
- For protocol-mismatch claims, prefer a live wire-level probe over source-level reasoning; the serde analysis alone would have produced a wrong triage verdict.
- Give delegated investigators explicit shell-fallback authorization when the system under investigation is itself the MCP surface.
