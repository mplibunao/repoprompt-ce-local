## Decisions made before the run

- Decision: fix test timing without weakening what each test proves; a product bug gets a product fix. Source: user.
- Decision: in-suite deadlines and a runner backstop are both needed. In-suite code can't bound a blocked executor, a synchronous deadlock, or teardown that ignores cancellation; a runner watchdog can't name the missing gate or carry the original admission error. Source: approved plan.
- Decision: in-suite bounds are 30 s per step, gate, condition, or task result; 60 s to acquire the suite gate; 30 s for per-test cleanup. They are failure guards, far above the suite's observed 1.7 to 6.1 s per run. Source: approved plan.
- Decision: `AdmissionTestSuiteGate.acquire()` gets a bound and the test keeps an `acquired` flag so `tearDown` releases only what `setUp` acquired. No ownership token and no "unusable gate" state: XCTest runs one test method at a time per process and the hosted runner gives each suite its own process, so a second holder can't occur. Source: design critique of the plan.
- Decision: a timed-out cleanup never restores the global storage override under a runtime that may still be writing; it fails the test naming the cleanup step instead. Source: approved plan.
- Decision: the Default regression runs both release orders. Each subcase waits for a positive sign that the released path finished (the canonical snapshot for the manager path; the bridge's initial projection for the bridge path, through a DEBUG-only `WindowState` accessor), then asserts activation stays absent for a short named window. A 30 s inverted expectation per subcase was rejected: it adds about 60 s per run and, without a positive sign, can't tell a working join from a slow release. Source: design critique of the plan.
- Decision: the local backstop is the conductor's existing `--xctest-stall-seconds` watchdog at 180 s on `make dev-test`; the hosted backstop is a per-suite timeout in `Scripts/ci_app_test_runner.py`, set from the changed suite's measured duration and a survey of recent hosted runs. Source: approved plan.

## 1. Bound every admission-suite wait; Default regression; mutation checks

- Decision: in the bridge-first subcase (bridge released, manager creation held), the oracle is that the window's initial activation switch hasn't run (`workspaceManager.isInitialized` stays false), not that `activeWorkspace` stays nil. The bridge's initial projection adopts Default as the active workspace through `applyDomainWorkspaceProjection` → `adoptProjectedActiveWorkspaceID` without awaiting `awaitDefaultWorkspaceReadiness()`; only the initial `switchWorkspace` task, which calls `completeInitialization()`, joins both owners. The manager-first subcase keeps `activeWorkspace == nil` and also checks `isInitialized`. A product change to make adoption wait was rejected: the final state is canonical and writable, and no failure has been traced to adoption. Source: orchestrator judgment, on the implementing agent's finding that the plan's premise was wrong.
- Decision: the four gate types keep one shared holding mechanism (`AdmissionParking` with `AdmissionParkedCallers`, arbitrated inside each gate's actor); gate entry also watches the producer task, so a start that throws before reaching the gate fails with its own error instead of a gate timeout. `waitUntilEntered()` and the entry waiters it needed are gone. Source: approved plan.
- Decision: a per-test `AdmissionTestCleanup` registry releases holds, cancels, then joins tasks and closes windows and runtimes within one 30 s bound, and restores the storage override only when that bound was met. It stays separate from `StartupTestTrackedOperations` in `AgentRunStartupTestSupport.swift`, which only cancels. Source: approved plan; the refactor review agreed.
- Decision: the refactor review's suggestion to share the two-statement wait-and-cancel sequence among `startupTestAwaitBounded`, `startupTestJoinBounded`, and `startupTestAwaitResult` was declined: a helper would add a name without removing logic that could drift. Its two comment corrections were applied. Source: orchestrator judgment.
- Evidence: the whole suite passed 10 of 10 runs under five load processes (300 test passes, 0 failures, 5.4 to 9.8 s per run). With admission forced to throw before provider dispatch, `testSecondWindowCannotStartPublishedProvisionalSessionBeforeAcceptance` fails in 4.5 s with the admission error instead of hanging. Removing the manager join from `awaitDefaultWorkspaceReadiness()` fails the bridge-first subcase (bridge released, manager held) with `isInitialized=true, activeWorkspace=Default`; removing the projection join fails the manager-first subcase (manager released, bridge held) with `activeWorkspace=Default` where nil was expected. Both mutations were reverted. `make dev-format`, `make dev-lint`, and the RepoPrompt build passed. Ten more loaded runs on the committed branch also passed (300 test passes, about 12 s per run including the no-op build), so 20 of 20 in all.
- Evidence: debug-app run, because `WindowState.swift` changed: `make dev-smoke-launch` packaged this branch's debug app and launched it, then stopped at `workspace switch` because window 1 was still restoring a 181-tab saved session; `make dev-smoke` against the same running app then passed (windows, workspace switch, roots, worktree list, agent roles). The new accessor has no caller in the app.
- Decision: the branch review's finding that a cleanup timeout releases the suite gate while the timed-out work may still run was declined. Holding the gate would make each later test wait 60 s and fail, about 30 minutes for the suite, which brings back the hang this change removes; the first failure names the cleanup step and says that the storage override and unclosed windows were left in place. Source: orchestrator judgment.

## 2. Runner backstops

- Decision: the hosted per-suite bound is 360 s. Three recent hosted `CI` runs (42019472798, 42142019101, 41953711633) had `MCPExportWatchdogIntegrationTests` as the slowest suite at 62.2, 56.8, and 50.8 s, so the plan's "at least 5x the slowest suite" rule needs at least 311 s; #175's figure of 29 s for the slowest suite is out of date. The admission suite took 1.9 to 2.8 s in those runs. The local stall bound stays 180 s, because it measures the gap between XCTest progress lines, which a single test has to exceed (slowest observed about 5 s). Source: orchestrator judgment, applying the approved plan's rule.
- Decision: the supervised executor leaves suite output inherited instead of capturing it to repeat the last XCTest start and finish lines in the timeout notice, as the plan described. XCTest writes each `Test Case … started` line as it happens (the conductor's watchdog read the stalled test's line while it hung), so that line sits directly above the notice in the log, and a capture pipe would add its own way to hang. Source: implementing agent's judgment, accepted by the orchestrator.
- Decision: the executor reaps the group leader before probing the group, and treats EPERM from `killpg` as "not gone yet": on macOS, signalling a group whose only member is an unreaped zombie leader returns EPERM, not ESRCH. Source: implementing agent's judgment, from a probe on this machine.
- Decision: the refactor review's suggestions to share launch code with `execute_command` or collapse the termination helpers were declined; its two smaller fixes were applied: the orchestration test no longer tracks a descendant, which the escalation test covers, and three comments state policy rather than certainty. Source: refactor review; orchestrator judgment.
- Evidence: a disposable test that never returns, run with `./conductor test --xctest-stall-seconds 20`, failed the job with exit 70 after 39 s; the job log names it (`XCTest progress stall watchdog triggered after 20.000s; current=-[RepoPromptTests.DisposableStallProbeTests testNeverReturns]`). `make -n dev-test` shows the 180 s flag and still forwards `FILTER` and `TEST_PRODUCT`. A full `make dev-test` with the flag passed 2,044 of 2,044 tests in 3 min 18 s; the slowest test took 6.6 s. `make ci-app-test-runner-selftest` passed 24 tests; its real-subprocess tests fail on the default executor reverted to `execute_command` (`0 != 70`), on signalling the leader only, on KILL without TERM, on raising instead of returning 70, and on a missing KILL deadline. `make conductor-selftest` and `make xcode-validate` passed.
- Decision: two branch-review findings on the executor were declined. Descendants that outlive a suite whose leader exited on its own aren't stopped; `subprocess.run` didn't stop them either, none has been seen, and #175 is about a suite that stops making progress. A SIGTERM aimed at the runner process alone leaves the suite running, as it did before; cancelling an Actions job sends SIGINT first, which the executor's interrupt branch handles, and the hosted macOS VMs are discarded after each job. Source: orchestrator judgment.
- Deferred: hosted CI on the pull request is the only run of the supervised executor on a macOS Actions runner.

## Evidence conventions

- Focused runs go through `./conductor test --filter <regex>`. Each attempt is counted from the `Test Case '…' passed|failed` lines in its job log, not the job's exit code: when a worktree's `.build` was seeded from another checkout, the conductor retries a failed job cold once and reports only the retry's exit code.
- "Under load" means five `yes > /dev/null` processes (about half of the machine's 10 cores) for the duration of a batch, on top of whatever the other worktrees were building; each run records the 1-minute load average.
- Baseline before any change, at `c4b5abfed`, 10 loaded runs: the whole admission suite passed 10 of 10 (29 or 30 passing tests per run, 9 to 10 s per run including the no-op build; 1-minute load 6 to 27). The hang #175 describes didn't occur in these runs; the fix is about bounding it when it does.
