## 1. Seeded publication locking and regression

- Decision: `SameThreadReentryCheckedLock.swift` and `GitWorkspaceAuthorityLockReentryGuardTests.swift` match upstream's files exactly, and `GitWorkspaceStateAuthority.swift` now matches upstream's post-image. The regression test didn't need signature adaptations: every store, Git worktree, planner, receipt, and instrumentation call it makes already matches this repository. Source: approved plan.
- Decision: `GitMetadataAcceptedWatermarks` gets the checked lock, a `defer` in `accept`, and the two review markers. Upstream's rewrites of its active-source methods aren't ported, because this repository's type doesn't have them. The store comment after the permit says the visibility assignment is linearized by "the authority permit," where upstream says "the recovery and authority permits," because upstream e4fb35ab's recovery permits were never ported. Every other comment hunk is verbatim. Source: approved plan.
- Decision: the regression test also asserts, after each seeded commit, that `publishedSeededAuthoritySnapshotForTesting` returns a snapshot for that root. Without it the test passes when a commit takes the full-crawl fallback, which skips the publication permit, because both routes leave one owned root. Only the permit closure creates published seeded authority for a new root, so a snapshot shows the permit ran. The snapshot's fields aren't asserted, because late Git metadata events can move them. This is the one place the test differs from upstream's. Source: review finding.
- Decision: the comment before the publication permit no longer says that no callback or task creation happens while the permit is held. The closure resumes paused ingress handoffs, which can schedule a drain task. The comment now says that nothing suspends inside the permit, that the drain's store work waits until the commit suspends, and that path-cache invalidation and seeded queryability checks stay outside the permit because both take its locks. Source: review finding.
- Decision: three review findings are declined, and the code they name stays as upstream wrote it. Source: orchestrator judgment.
  - Killing the child's whole process group would also stop a `git` grandchild still running when the 30 s ready deadline expires. That process ends by itself, and the case arises only after the test has already failed.
  - Checking that the mirror acquisition is nested inside the monitor callback, instead of comparing text order, would make the lexical guard much larger. The child-process regression is the behavioral evidence for the lock order.
  - A metadata event during the second root's asynchronous preparation could clear the primed path cache, so on unfixed code the commit might skip the deadlocking path and pass. The trigger held in both red runs, and pinning it would need a new DEBUG hook in the store's commit path that upstream doesn't have.
