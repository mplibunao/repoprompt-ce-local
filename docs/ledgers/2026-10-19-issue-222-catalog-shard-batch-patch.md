## 3. Measure, set the cap, prove the reproduction

- Decision: the matrix's modifications shape is keyed by input size and left out of the cap rule, because a modification never changes a record and so never counts as an effective edit. It still shows what a zero-edit batch costs. Source: orchestrator judgment, on the implementer's finding.
- Decision: add shapes stage files outside the root and rename them in, and subtree removal renames a folder out and back. Creating 4,096 files took 140–190 ms, close to the watcher's fixed 0.2 s window, so created batches would often split into two publications. Source: implementer measurement.
- Decision: an excluded attempt is retried, up to 10 extra attempts per cell, to reach 10 valid batches; comparison is armed on warm-ups too. Matrix roots are loaded one at a time, because `next` arms every loaded root and the window's search service re-merges all roots after each change. Source: implementer judgment.
- Decision: no extra matrix shape for removals scattered across folders, to keep the shared debug app's time down. Source: orchestrator judgment.
- Decision: numeric rules where the plan gives none, each marked in the analysis output: gate 3 and the copy-on-write check reuse gate 1(a)'s 2× limit; gate 4 fails when the last third's 90th percentile of outstanding publications exceeds max(10, twice the first third's) or the backlog grows at 0.05 publications per second or more; gate 6 passes when the post-cleanup footprint is within 10% of the first run's and no root holds more than 2 live generations at the end. Gate 1's 10,000-file bin spans 5,000 to 15,000 files, because the root grows about 1,500 files a second. Source: implementer judgment, accepted.
- Decision: the load test gives each worktree window a one-file idle root for its reader, puts light churn on three replica roots, uses depth 8 for worktree-sized roots, and alternates path and content searches. Source: implementer judgment, accepted.
- Evidence (debug app, 2026-10-20, built from `618ce194e` with docs-only uncommitted changes): the matrix ran 28 cells per root size at 10,000, 35,000, and 100,000 files, 10 measured batches each after warm-ups, with comparison armed. Parity matched in every batch, and no measured batch was excluded. Patch against rebuild medians at 4,096 effective edits: 118 against 253 ms (nested adds), 145 against 300 ms (spread adds), and 64 against 165 ms (subtree removal) at 10,000 files; 170 against 2,336 ms, 159 against 2,028 ms, and 79 against 1,990 ms at 100,000 files. At one effective edit, a patch took 0.1 to 8 ms and a rebuild 180 to 2,400 ms. The investigation holds the full table.
- Decision: the release cap is 4,096 effective edits. Every measured size passed the plan's rule at 35,000 and 100,000 files for every counted shape, so no crossover appeared and 4,096 is a lower bound; no larger cell was added, because a burst of more than 4,096 renames doesn't fit the watcher's 0.2 s window. The patch-to-rebuild ratio at 4,096 was 0.38–0.48 at 10,000 files, 0.11–0.20 at 35,000, and 0.04–0.08 at 100,000. Source: approved plan (the cap rule).
- Evidence: the merge copy, the one O(n) step left in a patch, took a median of 0.62 ms at 10,000 files, 2.2 ms at 35,000, and 7.3 ms at 100,000 (P95 1.8, 6.1, and 24.9 ms), copying two elements per file.
- Evidence: the plan's copy-on-write condition tripped. Per added file, the ingress mutation cost a median of about 176 µs at 10,000 files, 343 µs at 35,000, and 996 µs at 100,000, which grows with the root. At 100,000 files, 4,096 nested adds held the store actor for 8.2 s at the median and 25.3 s at worst, almost all of it ingress, past the 5 s cancellation grace. The cost doesn't depend on whether the batch then patches, so the cap stands. Per the plan, item 5 removes it before the reproduction.
- Evidence: a subtree removal's ingress cost per record doesn't grow with the root (26–34 µs at 201 records for all three sizes), so gate 3 holds; it grows with the subtree's size (about 33, 65, and 220 µs per record at 201, 1,024, and 4,096 records), which points at the per-child sibling-array removal the plan leaves in place.
- Evidence: rewriting 1,024 files in place sometimes reached the store as 982–1,023 modifications, and 4,096 as 2,050–2,540, across up to six publications. Code reading suggests that FSEvents collapses a burst into a folder-level rescan and that the watcher's one-level rescan compares names only, so it misses content changes. Unverified, and outside #222; parked below.

- Evidence: the file watcher's one-level folder scan filters the root's whole visited-path set on the watcher's own actor. At 550,000 files it can slow publications without adding a backlog, so Done-when (c) is judged on per-batch apply time and backlog, with the publication rate as context.

## 4. Twin-path fix

- Evidence: `NSString.standardizingPath` returns the same object when standardizing changes nothing, so a record's `standardizedFullPath` already shared `fullPath`'s object, one 224-byte UTF-16 `NSPathStore2`. Only the relative path was stored twice. The expected saving is about one allocation and 129 bytes per record, estimated from the scratch root set's path lengths, not the two allocations and 256 bytes the plan estimated. The heap capture is judged against the revised figure. Source: implementer finding, checked against the code; the parent orchestrating session accepted the revised target.
- Decision: the store builds each record's `fullPath` with `StandardizedPath.join`, a native Swift string, instead of `NSString.appendingPathComponent`. Without it the full-path helper saves no memory. Root full paths come from `URL.standardizedFileURL.path`, which has no doubled or trailing slash, so the bytes match. Source: approved plan (left to the implementer), decided from the probe above.
- Decision: the full-path fast path also requires at most 1,024 UTF-8 bytes, because `standardizingPath` truncates paths longer than 1,024 UTF-16 units. A file whose full path is longer still gets today's truncated `standardizedFullPath`; this change leaves that as it is. Source: implementer judgment, under the plan's rule that anything not provably unchanged takes the slow path.
- Decision: a new helper, `StandardizedPath.absoluteReusingStandardInput`, carries the full-path fast path instead of `absolute`, which has 217 callers. Source: approved plan.
- Evidence: `make dev-test FILTER=RepoPromptWorkspaceCoreTests` passed (11 tests), and with the length and prefix guards removed and `.` and `..` components accepted, 12 rows of the two new tests failed, each the row its guard protects. `make dev-test` passed 1,849 tests; `make dev-format`, `make dev-lint`, and `make dev-swift-build PRODUCT=RepoPrompt` were clean.
- Evidence: an independent review session found no code defects. It checked both fast paths against Foundation for look-alike prefixes, Unicode forms, a lone `/`, the empty string, and paths past the truncation limit, and `join` against `appendingPathComponent` for every root shape the store builds. A separate cleanup session made no changes.
- Evidence (debug app, 2026-10-20, 36 generated scratch roots of a real workspace set's sizes plus the debug profile's own repository window, 102,275 records on both sides): built from `7114d37b7` and then from `7bc8d9341`, each launched and reopening the same saved workspaces, `heap` counted 166,308 fewer `Swift.StringStorage` objects (10.5 MB) and 71,024 fewer `NSPathStore2` objects (17.0 MB): 2.32 fewer allocations and 269 fewer bytes per record. The `NSPathStore2` drop repeated within 3% across two runs; the string count varied by about ±0.8 per record between runs. Building `fullPath` with `join` accounts for the whole `NSPathStore2` drop, so it stays. A first run whose two sides had different workspace histories is excluded.
- Decision: the fast path moves into `StandardizedPath.absolute` itself, replacing the separate helper, so every caller that re-standardizes an already-standard path gets it back. Static path-match snapshots re-standardize record paths; with `fullPath` now a native string, Foundation allocated a new copy for each, about 31,500 `NSPathStore2` objects (7.6 MB) in the capture above. The result bytes don't change. The before-and-after capture is repeated for the final code. Source: orchestrator judgment, on the implementer's finding.
