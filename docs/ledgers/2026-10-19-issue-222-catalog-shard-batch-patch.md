## 1. One-pass batch patch

- Decision: no-op upserts and no-op modifications don't count toward the cap. With the release cap still 1, modification-only batches, re-added files, and a single-file add into a nested folder now patch instead of rebuilding. Source: approved plan.
- Decision: the two DEBUG arguments, `catalog_patch_cap_override` (0 to 1,000,000, where 0 restores the release cap) and `catalog_patch_comparison` (`on`, `next`, or `off`), are parsed in the `mcp_read_search_runtime_snapshot` handler. The `__repoprompt_debug_diagnostics` tool is matched by name before canonical routing and isn't in `tools/list`, so no schema snapshot changes. `next` arms one comparison per root loaded at that moment, for the matrix's forward-batch-only comparison. Source: approved plan for the arguments; implementer judgment for their ranges and the `next` value.
- Decision: a comparison mismatch is recorded as `parity_matched: false` rather than asserted, so it can't crash the shared debug app. The comparison rebuild's time is subtracted from the apply durations. Source: implementer judgment.
- Decision: the batch-sample history reuses the existing `recent_publication_limit` argument rather than adding a third. Source: implementer judgment.
- Decision: a removed folder's search key is `StandardizedPath.join` of the root's standardized full path and the folder's relative path, not a fresh `standardizingPath` call, which consults the disk and answers differently once a folder under `/private` is gone. A miss falls back to a rebuild. Source: implementer judgment, within the plan's rule to build the key as the store builds the folder's full path.
- Decision: the ancestry check covers inserted folders as well as inserted files, and an ancestor the same batch removes or displaces doesn't count as present. A modification and an upsert of the same ID in one batch resolve to the upsert. Source: implementer judgment.
- Decision: each sample records the whole apply two ways, from entering the canonical apply (including its waits) and the synchronous mutation pass alone. Input size counts upserts, removed IDs, and modified IDs; the no-op count includes collapsed repeats. Source: implementer judgment.
- Decision: `RootCatalogProjectionFile` is `Equatable` in all builds; a DEBUG-only conformance on the private nested type would need a duplicate declaration. Source: implementer judgment.

## 2. Off-actor rebase and ingress scans

- Decision: a rebase starts after a patch publishes when the root's path index holds 32 or more overlay payloads or the overlays mention at least max(2,048, n/16) entries, with no flight running for the root and live generations below the cap. The thresholds are `static let` constants that tests read, and item 3 tunes them. Source: approved plan.
- Decision: the trigger counts live shards directly instead of calling `canPublishAnotherRootCatalogShard`, which also increments a DEBUG backstop counter; the install still calls it. Source: implementer judgment.
- Decision: the capture holds the base object, the entries array, the overlay payload count, and the root's lifetime. The shard key, applied generation, and index identity aren't captured, because no install check reads them and the swap copies them from the current shard. Source: implementer judgment, narrowing the plan's capture list.
- Decision: the install requires the same flight, root, lifetime, and base object, and at least the captured payload count, keeps only the newer payloads, and publishes through a same-key initializer. A rebuild doesn't cancel a flight; its fresh base makes the install discard the result as stale. Source: approved plan.
- Decision: the overlay history owns the total payload count and gives the newest k payloads; item 1's copy of the count on the index is gone. An install counts under its own rebase counter, not as a full or overlay path-index build, and the detached build runs at utility priority. Source: approved plan for the counter; implementer judgment for the single owner and the priority.
- Decision: the subtree walk also serves the trash path, which the plan allowed when free, and keeps two results of the old prefix scan: a file stored at the folder's own path, and nothing for the root path. One `ancestorFolderKeys` helper replaces a duplicated parent walk. Source: approved plan; implementer judgment for the kept results and the helper.
- Decision: the traversal counters are cumulative per root rather than per batch sample, because the CodeMap invalidation walk runs before the apply pass that owns the sample. The payload also exposes the existing full and overlay path-index build counts, which gate 2 reads. Source: implementer judgment.
- Evidence: a rebase doesn't change catalog generations, so cached search snapshots keep the pre-rebase index, with its old base, until the next catalog change, normally the next patch. Results are the same; the memory shows in gates 6 and 8. Seeded worktree roots never rebase, because their projected index keeps its own overlay history.
- Decision: a rebase install evicts the store's cached search snapshots whose scope includes the root, through the same helper the cache-capacity eviction uses, without bumping catalog generations, which would invalidate CodeMap graph-index tokens and path-match snapshots. Source: review finding.
- Deferred: each window's search service keeps its own reference to a root's path index and refreshes it only on a catalog change. On a large root, where the base build outlasts the service's 50 ms debounce, the window holds the pre-rebase index until the next change, so an idle root can keep two bases. Results are unaffected. Freeing it needs a change event that lets windows swap one root's index; gate 6 measures whether that is worth a follow-up. Source: review finding, accepted as a known gap.
- Decision: the rebase test is named `testPathIndexRebaseKeepsNewerOverlaysAndDiscardsStaleResult`, because it checks both that an install keeps the newer overlays and that a stale result is discarded. Source: cleanup finding.
- Evidence: two review rounds found no blockers or should-fix items; the cleanup pass made two edits. After them the eight affected suites (45 tests), `make dev-format`, `make dev-lint`, and `make dev-swift-build PRODUCT=RepoPrompt` were clean.
- Evidence: the three item 2 tests pass, and each failed with its defect put in by hand (no base-object check at install, newest-payload slicing that skips pages, a walk that doesn't descend). Eight affected suites (45 tests) and the full `make dev-test` (1,853 tests) passed; `make dev-format`, `make dev-lint`, and `make dev-swift-build PRODUCT=RepoPrompt` were clean.

## 4. Twin-path fix

- Evidence: `NSString.standardizingPath` returns the same object when standardizing changes nothing, so a record's `standardizedFullPath` already shared `fullPath`'s object, one 224-byte UTF-16 `NSPathStore2`. Only the relative path was stored twice. The expected saving is about one allocation and 129 bytes per record, estimated from the scratch root set's path lengths, not the two allocations and 256 bytes the plan estimated. The heap capture is judged against the revised figure. Source: implementer finding, checked against the code.
- Decision: the store builds each record's `fullPath` with `StandardizedPath.join`, a native Swift string, instead of `NSString.appendingPathComponent`. Without it the full-path helper saves no memory. Root full paths come from `URL.standardizedFileURL.path`, which has no doubled or trailing slash, so the bytes match. Source: approved plan (left to the implementer), decided from the probe above.
- Decision: the full-path fast path also requires at most 1,024 UTF-8 bytes, because `standardizingPath` truncates paths longer than 1,024 UTF-16 units. A file whose full path is longer still gets today's truncated `standardizedFullPath`; this change leaves that as it is. Source: implementer judgment, under the plan's rule that anything not provably unchanged takes the slow path.
- Decision: a new helper, `StandardizedPath.absoluteReusingStandardInput`, carries the full-path fast path instead of `absolute`, which has 217 callers. Source: approved plan.
- Evidence: `make dev-test FILTER=RepoPromptWorkspaceCoreTests` passed (11 tests), and with the length and prefix guards removed and `.` and `..` components accepted, 12 rows of the two new tests failed, each the row its guard protects. `make dev-test` passed 1,849 tests; `make dev-format`, `make dev-lint`, and `make dev-swift-build PRODUCT=RepoPrompt` were clean.
- Evidence: an independent review session found no code defects. It checked both fast paths against Foundation for look-alike prefixes, Unicode forms, a lone `/`, the empty string, and paths past the truncation limit, and `join` against `appendingPathComponent` for every root shape the store builds. A separate cleanup session made no changes.
- Decision: reviews and cleanup passes run as fresh agent sessions bound to the item's worktree, from the templates in `.agents/skills/rpce-merge-pr-batch/references/review-prompts.md`, because a Context Builder run in the orchestrator's tab reads the main checkout rather than the worktree. Source: orchestrator judgment.
