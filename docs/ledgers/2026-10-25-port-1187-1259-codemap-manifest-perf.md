## 3. A/B CPU measurement and debug-app run

- Decision, a departure from the plan's protocol: the idle threshold was raised. The plan starts a run only when the debug app uses under 0.5 s of CPU over 30 s, which never happened. The debug app restored eight other windows, spent about 27 minutes at one full core on the baseline launch, then settled at a steady 1.4–1.9 s per 30 s. The first baseline attempt aborted after 30 minutes under the plan's rule and measured nothing. From then on, a run started once three consecutive 30-s samples were each at most 2.0 s, in both halves. The change was made before any run was measured. A constant floor adds the same CPU to both halves, which pushes the ratio toward 1 and makes the threshold harder to pass, not easier. Source: orchestrator judgment.
- Decision: the other windows stayed open, because no supported command closes a window without deleting its workspace. The plan's fallback applied: each run recorded the other windows' `write_count`, and none changed. Source: approved plan.
- Decision, a departure from the plan's protocol: CPU is compared per iteration, not per written publication, and the plan's rule that the `write_count` delta must equal the iteration count was set aside. Every branch run wrote 20 publications for 10 iterations. Each edit drops the file's record, because a file has a record only while its contents match its Git index entry, and the commit adds it back, so each iteration makes two record changes. Baseline publications took about 28 s each, so the writer merged the second change into the next write: 10 writes and 5 merged no-op attempts per run. The plan assumed one record change per commit, which held on the baseline only because it was slow. Both builds ran the same workload, so CPU per iteration compares like with like, and it's stricter on the branch than CPU per publication. The plan's per-publication metric is reported too, and it passes. The rule's purpose, catching publications from other sources, is covered by its other conditions, which all held: no other window's `write_count` changed, no heavy conductor job ran, and every write was captured as an attempt event from the scratch root. Source: orchestrator judgment.
- Evidence: baseline `e77df0333`, branch `d63e137eb`, both debug builds 1.4.0 (62), on the debug profile's store, 2026-10-26. CPU seconds per iteration: baseline 30.49, 32.89, 30.42 (median 30.49), branch 1.20, 1.14, 1.16 (median 1.16), a ratio of 0.038 against the plan's 0.5 threshold. Per written publication: baseline median 30.49, branch median 0.58, ratio 0.019. After subtracting each run's idle floor, the per-publication ratio is 0.014.
- Evidence: the reconcile remainder per written attempt (total duration minus the nine phase durations) had a median of 29.7 s on the baseline (30 attempts, 26.9–40.2 s) and 139 ms on the branch (60 attempts, 129–218 ms). Every branch attempt read 17–19 KB of input and decoded 0 bytes of target, which is live target reuse. Every baseline attempt decoded as many bytes as it read.
- Evidence: after warm-up the store held 263 manifests (87.4 MiB) in every baseline run and 261–263 (87.4 MiB) in the branch runs, a difference under 1%. It stayed above the 256-manifest cap in both halves although every written publication reconciles quota. That suggests at least seven files fail scan validation, but the diagnostics don't expose the store's valid and corrupt counts. Diagnostics polling cost about 0.05 s of app CPU per call: 2–3% of a baseline run's CPU and 16–19% of a branch run's, so the branch figures are pessimistic.
- Evidence: debug-app run on the branch build (`d63e137eb`, 1.4.0 (62)), in a scratch Git repository with 13 Swift files, one with a non-ASCII name. Graph indexing completed, and two code-structure requests for the same two files returned identical, correct symbols. An exact-path read of the non-ASCII file returned its content, and the file tree showed one root with all 14 files. Both code-structure requests reached the manifest store: one written and five unchanged attempts, each with 18,832 input bytes and 0 decoded bytes. There were no failures, retries, or queued work. The reuse came from snapshots the same app process had cached during the A/B runs, and the unchanged attempts return before any quota scan, so this run shows target reuse, not scan behavior.
- Evidence: the file tree printed the non-ASCII filename in decomposed (NFD) form, while the disk, Git, and the read result use the precomposed form. A read through the decomposed form resolves to the same file. The port doesn't touch Unicode normalization, and the baseline build wasn't checked for this.
- Evidence: production's process ID and start time were the same before and after the block. The debug app was left running the branch build with its original windows, and the scratch workspace and repository were removed.
