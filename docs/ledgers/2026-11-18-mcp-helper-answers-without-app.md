## 1. Shared capabilities, app display name, connection messages, offline responder, CLI wording

- Decision: the app server's capabilities are one value, `MCPAppServerCapabilities.value` in `Sources/RepoPromptDomainRuntime/`, which `BootstrapSocketConnectionManager` passes to `MCP.Server`. The helper's offline `initialize` result encodes the same value, because a later replay fails terminally when `capabilities` or `protocolVersion` differ. `RepoPromptDomainRuntime` already links the MCP SDK, so `Package.swift` doesn't change. Source: approved plan.
- Decision: `MCPOfflineResponder` is a pure value type: one frame in, at most one reply out, plus whether the caller records the frame for replay. It isn't wired into the proxy yet. It takes the server version as an initializer argument instead of reading `CLI_VERSION`, so tests can construct it; the proxy passes `CLI_VERSION`. Errors use the SDK's `MCPError`, so wire messages carry its prefixes, for example "Method not found: Unknown method: x" and "Server error: <message>". Source: approved plan; the version argument is orchestrator-accepted agent judgment.
- Decision: any client frame that carries an `id` but no `method` gets `-32600`. A silent reply would leave that id open in `JSONRPCBridgeLedger`, and `beginConnection()` would then refuse the later attachment with `reconnection_attempted_with_unreplayable_work`. `testOfflineRepliesCompleteTheirRequestsInTheBridgeLedger` guards this, beyond the two tests the plan named. Source: review finding.
- Decision: `MCPAppConnectionMessages` owns every connection text that names RepoPrompt CE or RepoPrompt CE Debug: the offline tool error, awaiting approval, approval denied, socket permission, bootstrap timeout, other transport failures, the offline `initialize` instructions, and exec's verbose retry lines. Exec and interactive print one `Error: <text>` line each through `InteractiveSessionError.description`, with their stderr destination, colour, attempt counts, and exit codes unchanged. The `.connectFailed(errno:)` mapping lives in `MCPAppConnectionMessages.connectFailure(errno:identity:)`. Source: approved plan; the single-line output and the shared mapping are refactor findings.
- Decision: the terminal catches in `main.swift` print `RepoPrompt MCP: <description>` as a second line. For approval denial that line now names the app, as it already did for the other connection errors. Source: orchestrator judgment, declining a refactor plan that added a separate formatter and a stderr-capture test file to keep the old short text.
- Decision: `appDisplayName` keeps its own mapping instead of returning `applicationSupportDirectoryName`. The two are separate concepts that share values today, and coupling them would let a directory rename change user-facing text. Source: orchestrator judgment, declining a refactor finding.
- Evidence: `MCPOfflineResponderTests` (3 tests) passes, including `testOfflineInitializeMatchesAppSDKHandshake`, which compares the responder's fingerprint with a real SDK server's over `InMemoryTransport` for every version in `Version.supported` plus an unsupported one. `MCPProxyTerminalRecordTests` (7), `MCPFilesystemIdentityIsolationTests` (17), and `CLIModeParsingTests` (3) pass. `make dev-swift-build` passes for `repoprompt-mcp` and `RepoPrompt`; `make dev-format`, `make dev-lint`, and `make guardrails` pass. ## 2. Proxy seams and offline startup with attachment

- Decision: `MCPProxySession` in `Sources/RepoPromptMCP/Transports/MCPProxySession.swift` owns the proxy's run: the first connection, offline startup, the one attachment worker, the handoff, and the connected relay with its existing reconnect loop. `MCPService.runTransport` builds its dependencies and throws the outcome. `MCPProxySession.run` takes the descriptors, socket URL, identity, server version, fault rule, retry wait, a phase observer, and a `logMessage` callback, so tests drive a whole session over pipes and a fake bootstrap socket. Source: approved plan for the test entry point; the parameter list is agent judgment the orchestrator accepted; the file and the callback are a refactor finding.
- Decision: `BootstrapSocketProxy` splits into `connectAndAccept`, `replayInitialize(timeout:)`, and `runAcceptedBridge`. The first attachment replays `initialize` with no deadline, so a person can take as long as they need on the approval prompt. A rejected replay ends the session with `SocketProxyError.initializeReplayRejected(code:message:)`, which keeps the app's error text. Source: approved plan.
- Decision: stdin framing moved into `MCPProxyStdinPump`, which the offline loop and the bridge both use. It stops only between complete frames and returns the unread bytes, so the handoff loses and reorders nothing. Source: approved plan.
- Decision: on its first attempt, a missing socket sends the helper offline at once. A refused connection, a bootstrap timeout, a transient rejection, or a socket permission error retries once after 0.5 s, then goes offline with that condition's message. The plan didn't name the permission case; it falls with the other present-socket failures. Source: approved plan; the permission case is agent judgment the orchestrator accepted.
- Decision: two attachment steps take a different route than the plan, with the same order on the wire. A client `notifications/initialized` that arrives after the replay is prepended to the unread stdin bytes, so the bridge writes it to the app first, instead of the worker writing it to the socket. The helper's `notifications/tools/list_changed` is prepended to the buffered app frames, so the bridge writes it to the client first. The plan's step for replaying queued requests is left out, because none exist at first attachment; item 3 adds it for the outage path. Source: agent judgment the orchestrator accepted.
- Decision: the top-level `log` in `main.swift` crashes when a test reaches it, because XCTest never runs that file's top-level code. `BootstrapSocketProxy` calls on the paths the tests drive use `debugLog` instead of `log.debug`, and the session receives its logging as the `logMessage` callback, which `MCPService` routes to `debugLog` and `log`. Session log messages are now built eagerly instead of through `debugLog`'s autoclosure; all five are on retry or stop paths. Source: agent finding; the callback is a refactor finding.
- Evidence: `MCPProxyOfflineStartupTests` (7) covers an absent app, late admission, a byte-preserving handoff, local answers never reaching the app, a rejected or mismatched replay, end of input while offline, and cancellation cleanup. `MCPProxyTerminalRecordTests.testFirstAttemptFailureDisposition` checks the first-attempt table. After the refactor, the 18 tests in those suites and `MCPOfflineResponderTests` pass, and `make dev-swift-build PRODUCT=repoprompt-mcp`, `make dev-format`, `make dev-lint`, and `make guardrails` pass. No live run yet; item 4 owns it.
- Review: the agent's review loop ran three rounds and ended with no findings. The refactor loop ran two rounds: one extraction, then clean.
- Left for item 3: reconnects after a connected session drops still run in `MCPProxySession.runConnectionLoop` with the replay's 5-second deadline, and a fingerprint mismatch there reports the generic `jsonrpc_bridge_terminal` reason.

## 3. Mid-session outage handling

- Decision: when the connected bridge's socket fails, the stdin pump stops at the next frame boundary and the bridge returns the failure and the unread bytes as `MCPProxyBridgeInterruption`. A failed write of a client frame does the same once its ledger accounting is done. Failures that end the session (termination, cancellation, a terminal ledger) still cancel the pump at once. The session then enters the `outage` phase: the offline loop answers new requests with the named-app error, and the same worker reconnects through the attachment sequence. Source: approved plan.
- Decision: the worker makes every connection after the first, with one retry schedule for the whole session that never resets, as `runTransport`'s loop didn't. `BootstrapSocketProxy.start()`, `replayInitializationOnStart`, the replay's 5-second deadline, and its `..._replay_timeout` reason are removed, and so is the replay's branch for an `initialize` with no delivered result, because the worker replays only after the client has one. The plan kept `start()`; nothing called it once reconnects moved to the worker. Source: approved plan; the removals are agent judgment and a refactor finding.
- Decision: replayable requests in flight at the outage are held for a 60-second grace, the same constant as the retry schedule's fast-retry window, which starts only when something is held. If the app returns in time they replay. Otherwise each gets the named-app error, which takes it out of replay so it never runs later. At a frame boundary an expired grace is handled before a pending handoff. A client cancellation of a held request removes it from replay, applied once per cancellation the ledger committed through `MCPOutstandingRequestReplayState.recordClientCancellation(for:)`. That method is the only change to `Sources/RepoPromptMCP/MCPReplayState.swift`, which the plan's file list left unchanged. Source: approved plan; the ordering and the cancellation handling are review findings; the typed method is a refactor finding the orchestrator accepted.
- Decision: a late client `notifications/initialized` is written to the socket before the held requests, the plan's step order, replacing item 2's prepend to the stdin bytes now that both paths meet. Source: approved plan.
- Decision: an `initialize` in flight at the outage is answered locally at once instead of being held, because the worker can't attach until the client has a result. If that `initialize` is invalid, the session ends with `missingInitializeResponseFingerprint`; the reviewer suggested discarding the cached handshake instead, and the agent declined because only a client sending an invalid `initialize` reaches it. Source: agent judgment the orchestrator accepted.
- Decision: a worker failure with a terminal ledger reason now terminalizes the ledger, so a fingerprint mismatch records `mcp_session_resume_initialize_replay_result_mismatch` instead of `jsonrpc_bridge_terminal`, at first attachment and after an outage. If a reply to the client is cut off mid-write, the ledger is already terminal, so the outage never writes after half a frame. Source: item 2's deferral; the mid-write rule is agent judgment.
- Decision: if the client half-closes stdin and the app then quits while responses are pending, the session now ends; before, it reconnected and delivered them. This follows the plan's rule that end of input while offline ends the session. Source: approved plan.
- Evidence: `MCPProxyOfflineStartupTests` now has 10 tests, adding `testToolCallDuringOutageGetsNamedErrorThenWorksAfterReturn`, `testReadInFlightAtOutageReplaysWhenAppReturnsWithinGrace` (which also checks that a cancelled held read never replays), and `testReadInFlightAtOutageGetsNamedErrorAfterGrace`. `testHandoffPreservesCompleteAndPartialUnreadFrames` covers both directions, and the rejection test checks the mismatch reason. Three throwaway mutations each failed a test: cancelling the pump instead of handing off, leaving a grace answer queued for replay, and dropping the cancellation handling. After the refactor, 25 tests across `MCPProxyOfflineStartupTests`, `MCPProxyTerminalRecordTests`, `MCPOfflineResponderTests`, and `PersistentMCPResponseDeliveryTests` pass, and `make dev-swift-build PRODUCT=repoprompt-mcp`, `make dev-format`, `make dev-lint`, and `make guardrails` pass. No test covers the grace-versus-handoff order; its only effect was a read replaying instead of failing within about a second, and a test would need both events gated at one boundary.
- Review: the agent's review loop ran three rounds, fixed three findings, and ended with none left. The refactor loop ran two rounds: two cleanups, then clean.
- Left for item 4: the live outage checks (plan live checks 8 and 9c) and the docs, including the half-close behavior above.

## 4. Live validation, before-and-after reproduction, and docs

- Decision: the "before" probe ran just before the branch's debug build replaced the installed one, once the running debug app had no agent session running or waiting for input, instead of earlier while other sessions' helpers were connected to it. Source: orchestrator judgment.
- Decision: during an outage, `tools/list` answers with the app's tool list instead of an empty one, and the helper sends one `notifications/tools/list_changed` when the outage starts. This replaces two lines of the plan: "A `tools/list` during the outage returns an empty list" and "No `list_changed` goes out at disconnect". Live check 8 showed why. As the debug app quits, it closes its windows, unregisters their tools, and sends `list_changed` before its socket closes. Claude Code re-lists. With the empty answer, Claude Code dropped every debug tool, and calls failed with "No such tool available" instead of the named-app error. A first fix remembered the last complete list the helper relayed. Three more runs showed Claude Code's re-list reaching the quitting app while its socket was still open, and the app answering with the 3 tools that need no window. So the remembered list now shrinks only at an attachment, and the outage `list_changed` makes the client re-list from the helper. During an outage every call fails with the named-app error, so overstating the list costs nothing, and the next attachment's `list_changed` restores the app's real list. The list lives in `MCPOutstandingRequestReplayState`, which already tracks each `tools/list` sent to the app; it is stored as the SDK's generic `Value`, so fields the helper's SDK doesn't define survive. Source: live evidence and orchestrator judgment, keeping the fix in the helper as the run's request decided; the storage choices are agent judgment the orchestrator accepted.
- Decision: Codex's one-run override needs `-c mcp_servers.RepoPromptCEDebug.enabled=true` as well as the command when the Codex config keeps the entry with `enabled = false`, because overriding only the command leaves the server off. `docs/testing.md` records it. Source: live finding.
