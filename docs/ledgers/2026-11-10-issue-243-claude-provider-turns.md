## 1. Provider start event and stream snapshot

- Decision: the controller withholds provider-owned output in production behind a private `forwardsProviderOutput` flag that only a DEBUG test hook sets, and the runner skips `.providerTurnStarted`. Until item 3 moves ingestion to the listener, the per-run consumer is the only reader, and forwarding would let a wake-up turn's output reach the next host run, as before #379. Item 3 removes the flag. A runner-side filter between a provider start and its completion was rejected: it would also drop host output when a provider turn picks up a host input, and drop everything when no completion arrives. Source: agent judgment, accepted.
- Decision: a result that only closes a provider turn now emits or defers a completion carrying the provider turn ID. This replaces the #379 rule that cleared `providerTurnID` when the result arrived, so the idle probe stays busy until Claude Code reports idle. Source: approved plan.
- Decision: `observeActivity` returns the output owner (host, provider, or none) instead of upstream's Boolean, and a private controller wrapper observes activity, announces a newly started provider turn, and returns that owner at all three activity sites (main-thread output, `command_lifecycle`, and `can_use_tool`). Source: agent judgment, then a refactor review finding.
- Decision: a `command_lifecycle` frame with a parent-tool key doesn't start a provider turn, matching the main-thread rule for other frames. Source: review finding.
- Decision: kept upstream's rule that a provider turn closes only on a result naming its execution. A wake-up turn whose assistant frames carry no input UUID but whose result carries one would stay open, and after this item it would also make the next host send interrupt it. #379's live run on Claude Code 2.1.319 saw no such stamping. Item 5's live run checks for it again. Source: orchestrator judgment.
- Decision (refactor gate): `DeferredCompletion.inputIDs` became `turnIDs` and `requiresHostOutputOwner` became `requiresRunOutputOwner`, because both now cover provider turns. Declined merging `eventStreamSnapshot`'s tuple with `NativeAgentRuntimeEventStreamHandle`: the plan approved upstream's snapshot-plus-derived-handle shape, which makes later ports easier. Source: refactor review, orchestrator judgment.
- Evidence: `ClaudeNativeTurnCorrelationTests`, `ClaudeNativeApprovalAndResumeTests`, `ClaudeIdleShutdownTests`, and `AgentRunStartupSnapshotTests` passed (49 tests), and after the refactor the first three passed again. `make dev-swift-build PRODUCT=RepoPrompt`, `make dev-format`, and `make dev-lint` passed. The agent broke the code five ways (start after output, no start on an approval request, provider turn left out of the in-flight state, adapter not forwarding the snapshot, orphan tool results counted as activity), and each break failed its test. The interrupt guard has no test, because `interruptTurn` fails without a live process.

## 2. Controller event listener and attempt inbox

- Decision: the listener keeps upstream's shape, so item 3 can port upstream's coordinator and runner calls closely. It has settable callbacks for adoption, busy changes, idle events, and stream end, a listener-and-inbox pair as the reservation, and an internal `receive`. Source: agent judgment, accepted.
- Decision: the inbox resets when it drains and otherwise compacts once 256 or more read events make up half its buffer. It never drops an event. Source: approved plan.
- Decision: hardening beyond upstream. Each inbox wait carries an ID, so a late cancellation handler can't release a later wait. Publication waits end when their task is cancelled. The publication fence holds every closed inbox whose publication is pending. A retired listener refuses `install` and `reserve`. `awaitTerminalPublication` re-checks the fence after every wake. Tail routing stops if the listener retires partway through. Source: agent judgment and review findings.
- Decision: `detachTransport` keeps steering and settlement-recheck events, which belong to the attempt, and drops the retired transport's output and provider turn IDs. A direct `install` keeps events already in the inbox, because they can include the attempt's own failure completions. Source: approved plan, review finding declined with that reason.
- Decision: cancelling a buffered approval also rewrites approval requests waiting in the provider handoff, not only those in the inbox. Source: approved plan.
- Decision (refactor gate): `detachTransport()` and `retire()` share a private `clearTransportState()`. Source: refactor review.
- Evidence: `ClaudeControllerEventListenerTests` (7 tests) covers: the reader surviving a cancelled wait; unread provider work moving to the next attempt in order, while idle output isn't kept; adoption waiting for the closed attempt's publication; transport replacement; retirement releasing every waiter; buffered approvals becoming cancellations; and delivery held during an input handoff. With `ClaudeNativeTurnCorrelationTests` and `ClaudeNativeApprovalAndResumeTests`, 28 tests passed, and the listener suite passed again after the refactor. `make dev-swift-build PRODUCT=RepoPrompt`, `make dev-format`, and `make dev-lint` passed. The agent injected 12 defects, and each failed its targeted test. The re-check after every publication wake has no test, because queue order can't force that interleaving without a scheduling hook in production code.

## 3. Ingestion cutover and provider-turn adoption

- Decision: the coordinator installs one listener per tab's Claude controller, and the runner reads the listener's inbox instead of the controller stream. Replacing a listener while a controller stays attached resets the controller's stream first, because cancelling the old reader ends its `AsyncStream`. The controller's `forwardsProviderOutput` flag and its DEBUG hook are gone. Source: approved plan, and agent judgment after item 2's note for the stream reset.
- Decision: a host start reserves the Claude inbox at the top of `startAgentRun`, before its first suspension, whenever a controller exists. That covers user turns, which take their ticket through `installStartupTicketIfAbsent` rather than `admitStartIfFree`. A start that can't reserve fails before dispatch with "No message was sent because another Claude run in this session is still active. Send it again when that run finishes." Source: approved plan; the message wording is orchestrator judgment, after a refactor review finding.
- Decision: adoption takes its own startup ticket and moves it through queued, preparing, and dispatching itself, because only `startAgentRun` moves a host ticket and adoption doesn't call it. `claimStartupRunID` keeps the installed process run ID, so the adopted attempt keeps it. When another start holds admission, the adoption leaves the turn to that start. A provider turn left waiting when admission is released is offered for adoption again. Source: approved plan, and a review finding for the re-offer.
- Decision: queued instructions don't block adoption by themselves. A follow-up entitled to start holds a ticket and so defers the adoption. Other queued instructions wait for the adopted attempt's terminal. Upstream's empty-pending-instructions guard isn't ported. Source: approved plan, agent judgment.
- Decision: buffered provider turns become protected predecessors at the coordinator's input handoff, not in the runner's `startRun` as upstream does. Every provider start, including a predecessor, opens a new transcript segment. Source: approved plan and review findings.
- Decision: `TerminalAnchor` on the terminal commit barrier is `.automatic` for ordinary runs, `.none` for a provider attempt and for a cancelled adoption ticket, and `.exact` for the user row added during an adopted attempt. Source: approved plan and a review finding.
- Decision: `observeRuntimeInit` only updates the provider session ID, because #364 isn't on `main`. Source: approved plan.
- Decision: to keep this commit from leaving provider work that Stop or the idle provider shutdown can't see, it brings forward from item 4: `claudeIdleRetirementBlocker` reports `.providerBusy` while a provider turn is pending, being adopted, or running; Stop during the adoption's wait phase withdraws the handoff and retires the provider work without creating an attempt, and Stop during its ticketed phase settles a cancelled start anchored to no user row; and an unexpected stream end, idle error, or failed runtime init is reported once per installation, to the attempt reading the inbox or else by retiring the controller. Source: approved plan (commit invariant).
- Decision (refactor gate): one private coordinator helper holds the controller retirement shared by Stop of a pending adoption and idle failure. `adoptProviderTurn` and `adoptClaudeProviderTurn` keep the plan's and upstream's names, and their doc comments say that `true` also covers a turn left to another start or stopped without adoption. Declined making the runner's `startRun` synchronous: it was already `async` before this item. Source: refactor review, orchestrator judgment.
- Deferred to item 4: a provider turn that Claude Code starts just before a host send, but that reaches the listener after the send begins, counts as a successor, and its failure fails the host run. Because of the same gap, the transcript has no boundary between a predecessor's output and the host's output. Fixing both needs an input-registered marker in the controller's event stream. Item 4 adds it and classifies starts by stream order. Source: review finding, orchestrator judgment.
- Deferred to item 4: steering-release and settlement-recheck producers (the consumer already handles their events); teardown joins across repeated Stops; binding transitions, which leave the listener non-current without detaching the controller; a failed terminal for an adoption rejected after its MCP epoch was prepared; the view model's retirement blockers and stale MCP busy-mask preservation; composer sends during the adoption's wait phase, which are refused although the plan lets a host start win there; and tests for the parts brought forward above. Source: agent report.
- Evidence: `ClaudeProviderStartedTurnTests` (3 tests) covers two idle provider turns becoming two attempts that keep the process run ID, don't add user rows, and publish once each; a final-only provider reply leaving the previous answer's text and ID unchanged; and tools and usage belonging to the adopted run without consuming queued input estimates. The suites named in the brief passed (120 tests). The full root suite ran 1976 tests with one failure, `MCPWorkspaceScopedCursorModelParameterTests.testSettingsPinnedCursorEffortAndSpeedReachRoleLabelRun` (`CancellationError` from the git-context refresh loop); that class passed alone (24 tests), and the change does nothing for a non-Claude session. Each committed test failed when its behavior was broken.

## 4. Races, Stop, idle failures, and the idle gate

- Decision: the controller emits `.inputRegistered(turnID:)` right after it registers a host input. The runner classifies a provider start before that event as a predecessor of the host input and one after it as a successor, and starts the host's transcript segment at the event. A successor's failure no longer fails a host input it didn't answer. Source: orchestrator judgment, after item 3's review found the race.
- Decision: a host start during an adoption's wait phase takes the provider turn. The startup refusal applies only once the adoption holds its ticket. Item 3 refused the start in both phases. Source: approved plan.
- Decision: before a steer or Stop interrupts Claude Code, it cancels every open Claude approval: the one the session shows, any still buffered in the inbox or provider handoff, and one the attempt already took. `withdrawApproval` on the listener tracks them. Source: approved plan and review findings.
- Decision: `sendClaudeNativeMessage` gains upstream's `inputAttemptChanged` callback, and a steer that failed after its write was attempted ends the attempt instead of releasing protected answers as successful. The settlement event's flag is `endsAttempt`, because it also ends the attempt when a steer fails after the process stopped and nothing replaced it. Steering checks cover running and waiting-for-approval. The steering-release and settlement-recheck producers are wired. Source: approved plan and a review finding.
- Decision: Stop keeps withdrawn provider retirements until they finish, so a later Stop that waits for teardown joins an earlier one, and the terminal shortcut joins them too. The repeated Stop with no terminal revision applies to Claude only. Source: approved plan, agent judgment.
- Decision: listener currency leaves out the binding-transition generation. While not current, the listener holds events, including a stream end or an idle failure, counts a held provider start as busy, and replays everything once admission frees. A failed binding transition can't leave it unable to accept events. Rebinding stops the process only when a previous provider session ID exists, as upstream does. Source: agent judgment and review findings. This departs from the plan's wording, which included the generation.
- Decision: an adoption refused after its MCP epoch was prepared publishes one failed terminal anchored to no user row, with the runtime failure message when one exists. An idle failure waits for the adoption task so it's reported once. Source: item 3's deferral list, agent judgment.
- Decision: also fixed from item 3: when a process was replaced mid-run, a provider turn whose completion the run hadn't read stayed in the expected and superseding sets forever, and a stream end that arrived while a binding transition began was dropped. Source: review findings.
- Decision (refactor gate): `cancelRun`'s three early returns share one wait helper, the overlapping approval test is narrowed to the provider-handoff case, and one `AgentTabSession` method holds the approval-dismissal state change that the coordinator and runner shared. Declined replacing `inputAttemptChanged`'s Boolean with a plain notification, because its signature matches upstream PR 1565. Source: refactor review, orchestrator judgment.
- Deferred: output that a predecessor writes after the input-registered event shares the host's segment, so a final-only host reply can replace the predecessor's final row. A completion can't mark the boundary, because the controller defers completions until Claude Code's idle signal and a queued host input starts without one. Tracked in #383. Source: review finding, orchestrator judgment.
- Deferred: a listener that remains not current while holding a provider start keeps the session busy until the next `eventListener(for:)` call replaces it, as a stale listener with a pending turn already did. A provider turn whose first frame arrives after the host write counts as a successor. Source: agent report.
- Evidence: `ClaudeProviderStartedTurnTests` gained 15 tests, `ClaudeIdleShutdownTests` 1, and `ClaudeControllerEventListenerTests` 2, covering the send-window race, approval-first Stop, send and steer ownership, Stop in each adoption phase, follow-up preservation, teardown joining, idle protection including held provider work, the idle race window, the re-offer of a provider turn left waiting, and a refused adoption's failed terminal. The full root suite passed (1994 tests in `RepoPromptTests`, 0 failures), as did the nine named suites, the product build, format, and lint. The agent reverted each fix and saw its test fail. No test covers: two-window isolation (each window has its own coordinator, so no plausible defect breaks it); the view model's `retireProviderIfIdle` blocker (the coordinator idle test covers the busy check); the repeated Stop with no revision; and steering while waiting for approval, which the fixture can't hold deterministically. The review fixes for retirement accounting, the stream end held during `onStreamEnd`, and a steer failing after a process replacement have no test, because no harness replaces the process mid-run.
