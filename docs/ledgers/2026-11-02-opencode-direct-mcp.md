# Run ledger: OpenCode direct MCP tools

Request: none · Plan: `opencode-v2-codemode-2026-11-02.md`

Make OpenCode 2.x list RepoPrompt's own MCP tools to the model as direct tools, instead of only through its built-in `execute` tool ("Code Mode"), by adding `codemode: false` to RepoPrompt's OpenCode MCP entry, without changing OpenCode 1.x behavior.

## Run decisions

- Decision: add `"codemode": false` to the active entry built by `OpenCodeIntegrationConfiguration.mcpConfigDict(for:)` and send it to every OpenCode version, with no version detection. OpenCode 2.x honors the key in the 1.x-shaped `mcp.<name>` entry and lists the server's tools directly, excluding them from `execute`; OpenCode 1.18.31 and 1.19.5 decode config with excess properties ignored and drop it. Source: user (approved plan).
- Decision: the same builder feeds interactive Agent Mode, headless discovery and Context Builder, and the explicit OpenCode install, so all three get the field; the disabled entry used by model polling and Chat/Oracle, the empty ACP `mcpServers`, and the managed permissions are unchanged. Source: user (approved plan).
- Decision: tool-name parsing is unchanged unless a captured OpenCode 2.x payload carries RepoPrompt identity in a form the explicit grammars reject. OpenCode 2.2.5's source names a direct call `RepoPromptCE_<tool>`, which they accept. Source: user (approved plan).
- Decision: keep only the contract test that fails on `main`; run the forced-`ask` permission scenario only if a normal live run shows a permission prompt for a RepoPrompt tool. Source: user.
- Decision: the headless permission gap on OpenCode 2.x (`execute`, `experimental_image_generate`, `external_directory`, MCP-resource actions) stays out of this change and goes to a separate issue, drafted for approval before filing. Source: user.
- Decision: the run works in its own worktree on `bugfix/opencode-direct-mcp`, branched from `main` at `1f9f8b116`. Source: orchestrator judgment, so the run doesn't change the main checkout or other runs' worktrees.

## 1. Overlay field, contract test, and config compatibility

- Decision: `testManagedLaunchKeepsDirectMCPConfigInOverlay` in `Tests/RepoPromptTests/AgentMode/OpenCodeACPLaunchResolverTests.swift` checks that `mcp.RepoPromptCE.codemode` is a JSON Boolean `false` (by `CFBooleanGetTypeID`, because `as? Bool` also accepts the number `0`) for the `.agentMode` and `.headless` profiles, and that new and resumed sessions send empty `mcpServers`. It uses a real executable from the suite's helper as the MCP command and `cleanupLegacyPersistentConfig: false`, so it never touches the user's OpenCode config. Source: approved plan; the Boolean check is the implementing agent's judgment.
- Decision: the overlay for the compatibility checks came from a throwaway test printing `ephemeralACPConfigJSON(...)`, run before and after the change and deleted before commit; the 2.x-shaped file came from OpenCode 2.2.5's own `opencode mcp add --global`, merged with a copy of `ensurePersistentMCPConfig()`'s logic, because the real installer writes to the real home folder. Later 2.x checks used `--standalone` so no background service kept running after the command. Source: approved plan for the overlay; orchestrator-accepted agent judgment for the rest.
- Evidence: the test failed before the change ("codemode missing") and passes after it; `OpenCodeACPLaunchResolverTests` 9 of 9 and `OpenCodeACPModelDiscoveryTests` 13 of 13 pass; `make dev-format` changed nothing; `make dev-lint` and `make dev-swift-build PRODUCT=RepoPrompt` passed; the commit preflight passed. A Context Builder review of the diff found no defects.
- Evidence (isolated `opencode debug config`, sandboxed home): OpenCode 2.2.5 resolves the overlay to `mcp.servers.RepoPromptCE` with `"codemode": false`; OpenCode 1.18.31 exits 0, drops the key, and resolves a config byte-identical to the pre-change overlay's; the disabled overlay stays off on both; an unrelated sibling entry resolves unchanged on both; on 2.2.5 a file with `mcp.servers.other` plus a flat `mcp.RepoPromptCE` normalizes to `mcp.servers` holding both, so reinstalling over a 2.x-shaped file works.
- Deferred: whether a RepoPrompt-launched OpenCode 2.x process lists the tools directly to the model is item 2's live check.

## 2. Live debug-app acceptance and docs note

- Decision: Design E case 1 applies, so no identity or normalizer change was made and the conditional identity extension was dropped. Direct calls arrived with `name` and `title` `RepoPromptCE_<tool>` (`get_file_tree`, `read_file`, `workspace_context`, `manage_selection`, `prompt`) and `kind: "other"`; in-progress updates carried the same `title` and `kind` without `name`; completed updates carried only `toolCallId`, `status`, `content`, and `rawOutput`; RepoPrompt normalized the calls to `mcp__RepoPromptCE__<tool>`. Source: live capture.
- Decision: the debug profile hides non-role models from MCP agents, so the run used `openCode:deepseek/deepseek-v4-pro`, built from the app's OpenCode model catalog and the `<agent>:<model>` format, which the app resolved to "OpenCode · deepseek/deepseek-v4-pro". The headless and Chat/Oracle runs needed the debug profile's Context Builder agent and model and its planning model pointed at that model for a few minutes; each was restored and read back. Raw ACP capture used `RP_OPENCODE_ACP_RAW_CAPTURE_PATH`, set with `launchctl setenv` for the debug-app launch and unset afterwards (confirmed unset). Source: implementing agent's judgment, accepted by the orchestrator.
- Evidence (debug build `a0a9f2e93`, OpenCode 2.2.5, DeepSeek V4 Pro, disposable `/tmp` workspace): the interactive run returned a fixture marker absent from the prompt through direct `RepoPromptCE_get_file_tree` and `RepoPromptCE_read_file`, each with one correctly named card, results matched by `toolCallId`, and no `execute` call referencing `tools.RepoPromptCE`; the headless Context Builder run returned the marker through direct calls with neither headless decline message; no `session/request_permission` occurred, so the forced-`ask` scenario did not run; model polling and Chat/Oracle launched OpenCode with the disabled entry (`enabled: false`, `/usr/bin/false`, no `codemode`) and started no RepoPrompt helper, and Chat/Oracle completed. The Agent Mode and headless processes received `mcp.RepoPromptCE.codemode` as a JSON Boolean `false`, read from their process environment.
- Evidence: `~/.config/opencode/opencode.json` was absent before the first and after the last debug-app OpenCode run, so legacy cleanup had nothing to touch. The docs change was reviewed with Context Builder: its finding that "other servers stay in Code Mode" overstated things was applied, its request to qualify the active entry was applied in part (the disabled entry for Chat, Oracle, and polling is now named), and its timeout finding was first deferred, then applied in item 3.
- Deferred: in every fresh OpenCode 2.2.5 process the model's first step ran before RepoPrompt's tools were listed; OpenCode then announced a changed tool catalog (about 19 s into the interactive run, 4 s into the headless one) and later steps used direct calls. This is OpenCode issue 51812, with open OpenCode PR 58374, and it is not caused by this change.
- Deferred: the existing `execute`→`bash` mapping renders a completed `execute` call as a failed `bash` card. Existing behavior, not touched here.

## 3. Contribution gates and pull request

- Decision: the independent review and the refactor pass ran in fresh `pair` sessions from the review and cleanup prompts in `.agents/skills/rpce-merge-pr-batch/references/review-prompts.md`, not under the engineer role, because during this run the engineer role mapped to OpenCode with DeepSeek, the provider this change fixes, on a production build without the fix. Source: orchestrator judgment.
- Evidence: the independent review found no defects in the source change or the test, and confirmed every active RepoPrompt OpenCode entry goes through `mcpConfigDict(for:)`. On the docs it found one should-fix and three nits, all applied: the install keeps the rest of `~/.config/opencode/opencode.json` only when the file is plain JSON, because `ensurePersistentMCPConfig` replaces a file it can't parse (for example one with comments or trailing commas, which OpenCode accepts); the Settings path is MCP Server → Quick Setup → Install MCP… → OpenCode; Agent Mode and Context Builder send the active entry on their agent runs, while their model and effort probes send the disabled one; reinstalling resets a custom `timeout`, so users with one add `"codemode": false` by hand.
- Evidence: the review's open question was checked on OpenCode 2.2.5 in a sandboxed home: `opencode mcp add --global` on a file holding a flat `mcp.RepoPromptCE` writes the new server under `mcp.servers` and leaves the flat entry in place, which still resolves with `"codemode": false`; the install replaces that same flat entry, so no duplicate `RepoPromptCE` entry appears. OpenCode 2.2.5 also accepted an `opencode.json` with a comment and trailing commas.
- Evidence: the refactor pass removed one repeated clause from the OpenCode notes and left the source comment, the test, and the remaining docs unchanged, with reasons. `pr-ready` ran before the first push; its result is in the pull request description.
- Decision: after the pull request opened, the OpenCode timeout bullet in `docs/architecture/provider-plugins.md` was corrected in this pull request. It had told users to set `"timeout": 10000000` on the installed entry, which lowers the installed 14,400,000 ms value and doesn't reach Agent Mode or Context Builder runs, because those runs send their own entry in `OPENCODE_CONFIG_CONTENT`. Source: user.
- Evidence: in a sandboxed home, OpenCode 2.2.5 `--standalone debug config` loaded a global `opencode.json` entry with a 1,000 ms timeout first and the `OPENCODE_CONFIG_CONTENT` entry with 14,400,000 ms after it. Later sources override earlier ones, and OpenCode's config documentation lists the same order. Vale flagged only the product name Agent Mode in the bullet.
- Decision: the installer replacing an `opencode.json` that isn't strict JSON stays a documented limitation, with no separate fix (Parked decisions). Source: user.
