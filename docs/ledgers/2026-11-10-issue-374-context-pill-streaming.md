# Run ledger: context pill work during streaming

Request: distribution issue #374 · Plan: a local Deep Plan, not committed

Stop the context pill from recomputing its selection summary, and the pill and context drawer from building worktree-binding resolution snapshots, on most streamed chunks of an Agent Mode reply, while the pill still follows selection, binding, and tab changes. Show the change with before and after counts.

## 1. Baseline attribution on `main`

- Decision: the hosted XCTest harness and its DEBUG-only instrumentation aren't committed. They're adapted from the harness that PR #378 measured with, and the after run in item 4 reuses them with hooks moved only to follow the changed code. Source: approved plan.
- Evidence: a hosted `AgentModeDetailWithSidebarView` streamed 20 synthetic Codex chunks per scenario on `403c210a8` plus instrumentation. Scenarios: the `rich` and `narration` workloads, each with no selection and with a fixed selection of one full file, one sliced file and one manual codemap, and each with the drawer closed and open. All 240 measured chunks were valid, and a repeat run gave identical summaries.
- Evidence, before counts: each chunk that changed the runtime snapshot (all 20 in `rich`, 12 of 20 in `narration`) cost 3 worktree-binding resolution snapshot builds: 1 from the pill's fallback through `AgentStatusPillsRow`'s bindings provider, and 2 from the context drawer reading `modelRequestIdentity` (its count pill and its `.onChange`). It also cost 1 pill `selectionSummary(for:)` call and 1 drawer body. The counts were the same with the drawer closed and open: the inspector keeps the drawer mounted, and the drawer observed `runtimeVM`. No other caller built a snapshot in any phase. The pill used its fallback on every chunk, because a selection-less publication cleared the detail view's live summary before streaming started.
- Finding for item 3: the workspace manager's debounced `$selectedFiles` sink (`WorkspaceManagerViewModel.swift:2599-2612`) rewrites a tab's stored `selectedPaths` into file-tree order without a `WorkspaceSelectionCoordinator.changes` event. In the harness the set of files stayed the same and only the order changed.
- Review: the item's `context_builder` review of the harness raised four measurement-validity findings, all fixed: summary calls and export-source builds now have separate counters, the drawer-open gate uses a per-scenario baseline, stdout no longer prints a path, and dropped diagnostic records invalidate a chunk. The follow-up review raised only nits.

## 2. Selection-only resolution and DEBUG counters

- Decision: `AgentContextExportSourceBuilder.resolveSelection` decides the tab and selection precedence: the requested tab, else the selection snapshot's tab, else the active compose tab, with the snapshot's selection used only when its tab matches. `makeSource` and the drawer's `selectionSummary` use it, and the summary doesn't call the bindings provider. Model requests and exports keep the full source. Source: approved plan.
- Decision: the two DEBUG counters, `context.selectionSummary.compute` and `context.exportSource.worktreeBindingsLookup`, sit in `AgentContextExportResolver.swift` rather than beside `makePersistentBindingResolutionSnapshot`, so they don't overlap PR #378's hunk and keep counting view-path lookups on a build that includes it. Source: approved plan.
- Evidence: `testSelectionResolutionPreservesSourcePrecedence` (8 labeled rows) passes; `make dev-format`, `make dev-lint` and `make dev-swift-build PRODUCT=RepoPrompt` pass.
- Review: the item's review and its follow-up found nothing. Refactor gate: the refactor review found nothing material. It kept the second compose-tab lookup in `makeSource`, because removing it would widen the selection-only helper for no measurable gain.

## 3. Store retention and scoped publication

- Decision: the store keeps a tool-result boundary. A retained live selection ends when a new `manage_selection` or `workspace_context` item, compared by item ID and result JSON, reports a file count different from the retained one. `testStaleLiveZeroDoesNotMaskNewerManageSelectionCount` stays. Source: the approved plan's fallback rule, triggered by the check below.
- Evidence for the fallback: the workspace manager's debounced `$selectedFiles` sink (`WorkspaceManagerViewModel.swift:2599-2612`) writes the active compose tab's selection through `publishActiveComposeTabSnapshot` and `updateComposeTabFastNoDirty` without a `WorkspaceSelectionCoordinator.changes` event. It rebuilds the selection from the files the file tree has found (`WorkspaceFilesViewModel.swift:11589-11603`), so it can drop paths and slices, not only reorder them. The 150 ms debounce can land after a compose-tab switch finishes.
- Decision: the pill's fallback resolves the active compose tab's selection through `resolveSelection`, and `AgentStatusPillsRow` no longer passes it a tab, session or bindings provider. The detail view publishes `.replace` or `.clear` only for `agentModeVM.currentTabID`, and re-reads the canonical selection on coordinator events instead of trusting the event payload. Source: approved plan.
- Decision: the survival test's rows follow the fallback. Row 1 starts from an older 3-file `manage_selection` result against a 1-file sliced live selection, and row 2 is a new result with the same count. The kept `testStaleLiveZeroDoesNotMaskNewerManageSelectionCount` covers a new result with a different count. Source: the plan's fallback rule, applied by the item's agent.
- Deferred: #385. The debounced write above can land after a compose-tab switch, and the tool-result boundary doesn't cover it, because that write doesn't produce a tool result. The pill then keeps a stale summary until the next selection event, tab switch or detail-view appear. Closing it needs the workspace manager's commit to go through the coordinator, which is outside this change.
- Evidence: `testLiveSelectionSurvivesTranscriptOnlyUpdates` failed on both rows before the store change and passes after it; `AgentRuntimeSidebarViewModelTests` (15 tests) and `AgentContextExportSourceBuilderTests` pass; `make dev-format`, `make dev-lint` and `make dev-swift-build PRODUCT=RepoPrompt` pass.
- Review: the item's review didn't find a production defect. One test nit was fixed: each boundary row now checks for nil both right after crossing the boundary and again after returning to the original tab. The follow-up found nothing. Refactor gate: the refactor review found nothing material.

## 4. Drawer observation, binding signal, and after measurement

- Decision: `AgentContextControlDrawerView` holds `runtimeVM` without observing it, and `AgentContextDrawerTokenEstimatePill` still observes it. `AgentStatusPillsSnapshot.contextLookupIdentity`, set from `agentWorkspaceLookupContextIdentity(tabID: currentTabID)`, which fingerprints the held session's bindings without a resolution snapshot, flows through both presenter constructions into `AgentContextDrawerSwitchKey`. A binding change then refreshes an open drawer, and a closed drawer refreshes when it opens. Source: approved plan.
- Decision: a `@State selectionChangeRevision` in the drawer, bumped by its existing selection-change handler while it's open, makes the drawer re-read the selection after a selection change. Without the runtime observation nothing else re-ran the drawer's body, and on the Context Builder tab the Selections count would have kept the previous selection. Source: the agent's judgment, accepted by the orchestrator, because it runs only on selection events.
- Deferred: #385, comment added. The debounced write recorded under item 3 also leaves an open drawer's Selections count stale until the next coordinator event, tab switch, prompt change or reopen; on `main`, the next streamed chunk re-read it.
- Evidence: `make dev-format`, `make dev-lint`, `make dev-swift-build PRODUCT=RepoPrompt`, `AgentRuntimeSidebarViewModelTests` and `AgentContextExportSourceBuilderTests` pass.
- Review: the item's review traced the binding-change path for an open and a closed drawer and found it sound, with no fixes. Refactor gate: the refactor review found nothing material.
- Decision: the after measurement runs in item 1's agent session, which built the harness. Source: orchestrator judgment.
- Evidence, after counts: the same harness, fixture and scenarios on the fixed source, with the instrumentation hooks moved only to follow the changed code. Per chunk that changes the runtime snapshot, binding builds fell from 3 to 0, pill fallback summaries from 1 to 0, drawer export-source builds from 2 to 0, and drawer bodies from 1 to 0, with the drawer closed and open. `ui.body.statusPills.context` stayed at 1, because usage changes still re-run the pill. The pill showed the retained live summary on all 240 measured chunks, and the committed DEBUG counters read 0 on every chunk. Warm-up builds fell from 18 (`rich`) and 12 (`narration`) to 0, and reply completion from 9 to 6. All 240 measured chunks were valid.
- Evidence, transitions: a selection change mid-reply reached the pill before the next chunk. Opening the drawer mid-reply left the pill unchanged. A binding change with the drawer open changed its switch key and refreshed it with the new binding. A binding change with the drawer closed refreshed it on open. Each transition was followed by 3 streamed chunks with 0 builds. The harness replays `commitWorktreeBindings` against a plain directory, because a full binding transition needs a real Git worktree, and binding changes ran idle, because the app refuses them during a running turn.
- Deferred: #388. Each drawer render outside streaming still builds 6 to 13 binding resolution snapshots, because the drawer and its Files tab, which stays mounted while the drawer is closed, read `modelRequestIdentity` from several getters, and each read rebuilds the export source. After this change, that cost occurs on transitions and reply completion, not on streamed chunks.
- Evidence, live before: on a debug build of `main` with other open pull requests merged and without this branch, one 60-line Codex reply in a tab with one full file, one sliced file and one manual codemap made 125 runtime-metrics store updates. 120 of the published updates had `selectionFileCount=nil` and `selectionSliceRanges=nil`. Only the detail view's 3 live pushes had 3 files and 1 slice range. `ui.body.statusPills.context` rose by 126.
