# Headless MCP domain runtime

The RepoPrompt CE MCP executable supports three session backends:

```bash
repoprompt-mcp --backend app
repoprompt-mcp --backend headless
repoprompt-mcp --backend auto
```

`app` remains the default for MCP stdio mode until explicit live and release validation supports a later cutover. `auto` is an explicit preview mode: it performs one bounded connect-only probe of the well-known app bootstrap socket before reading `initialize`, then fixes the selected backend for the process lifetime. It never probes private headless child endpoints and never switches an initialized session. `app` preserves proxy reconnect/replay behavior; `headless` composes the direct runtime. Interactive and exec modes are app-only and reject both `--backend headless` and `--backend auto`.

## The `app` backend while its app is unreachable

In `app` mode the helper, `repoprompt-mcp`, connects to its app's bootstrap socket before it reads stdin. The helper's build flavor picks the app: `RepoPrompt CE` for release and `RepoPrompt CE Debug` for debug. When the first attempt doesn't find a socket file, the helper answers the client itself at once. When the socket file exists but refuses the connection, the bootstrap handshake times out, or the app rejects the connection with a transient reason, the helper retries once after 0.5 seconds and then answers the client itself. The retry keeps an app that is starting or busy from costing an Agent Mode run its tools, because app-spawned provider children also run the helper with `--backend app`. Once the app accepts the bootstrap connection, the client's `initialize` waits for the app's admission, and the helper doesn't limit that wait.

`MCPOfflineResponder` answers the client while the app is unreachable:

- `initialize` gets a result with the app's capabilities, the shared `MCPAppServerCapabilities` value, and the protocol version the SDK would negotiate. Its server name is the app's display name, and its instructions say that RepoPrompt tools need that app with its MCP Server enabled. The app's own instructions depend on Settings, so the helper doesn't reproduce them, and a client initialized this way keeps these instructions after the helper attaches.
- `prompts/list`, `resources/list`, and `resources/templates/list` return empty lists. `tools/list` returns an empty list until the helper has relayed a complete tool list from the app: the app's reply to an unbatched `tools/list` without a cursor, whose result has no `nextCursor`. After that, `tools/list` returns the list the helper remembers, as the app sent it.
- `tools/call` returns one text item with `isError: true` that names the app and says to start it and enable MCP Server in Settings > MCP. `prompts/get` and `resources/read` return a JSON-RPC error whose message contains the same text. A request the helper answers itself is never queued, so it never runs in the app later.
- `ping` succeeds, and other methods, such as Claude Code's `server/discover`, get "method not found".

`MCPAppConnectionMessages` owns these texts, the message shown while the app waits for a person to approve the client, and the connection errors of `-e` and `-c`, which name the app as well.

Once the client has its `initialize` result, one worker keeps trying the app on the helper's retry schedule: every 0.5 seconds for the first 60 seconds after the first failure, then backing off to one attempt every 30 seconds, with no overall limit. When an attempt connects, the worker replays the client's cached `initialize` to the app, which admits it as it admits any client, including an approval prompt, and the helper doesn't set a deadline on that. The app's result must match the local one in capabilities and protocol version. If it doesn't, or the app refuses the client, the session ends, and the helper writes the app's message to stderr and to the terminal record. Otherwise the helper hands stdin to the relay at a frame boundary, with every unread byte in order, and sends the client `notifications/tools/list_changed`. A client that lists tools again on that notification, such as Claude Code, gets the app's tools in the same session. Codex 0.166.0 ignores it, so a Codex session started while the app was unreachable has no RepoPrompt tools until its next session.

When the app goes away during a session and the bridge ledger, `JSONRPCBridgeLedger`, allows a reconnect, the relay hands stdin back at the next frame boundary, the helper answers the client itself with the same texts, and the same worker reconnects. As the app quits, it closes its windows, shrinks its tool list to the tools that don't need a window, and sends `notifications/tools/list_changed`. A client such as Claude Code then lists tools again, and the app can answer that request before its socket closes. For that reason, within one attachment, a complete list with fewer tools than the remembered one doesn't replace it. The first complete list after each attachment does, even a shorter one, because the app's catalog may have changed while it was away. When the session enters an outage with a list remembered, the helper sends the client one `notifications/tools/list_changed` before it answers any request. The client then lists tools again and gets the remembered list. A tool call during the outage gets the named-app error. Requests in flight at the disconnect that `JSONRPCBridgeReplayPolicy` lists as replayable are held for 60 seconds: if the helper reattaches in time they replay, and otherwise each gets the named-app error, or the remembered tool list for a `tools/list`, and is never replayed. In-flight work that can't be replayed ends the session, as before. If the client has closed stdin and the app then quits while responses are pending, the session ends instead of reconnecting to deliver them. End of input while the helper is answering for itself stops the worker, and the helper exits.

## Ownership

`RepoPromptDomainRuntime` owns the protocol-neutral MCP host and canonical 27-tool catalog. It owns connection generations, invocation admission, policy/resource lanes, progress, watchdogs, settlement, terminal fencing, response-delivery accounting, and bounded drain. The app's `ServerNetworkManager`, `ServerController`, and `MCPService` are transport, presentation, proxy, reconnect, replay, listener, and approval adapters.

The app adapter also decides which Agent Mode run a bootstrap connection joins, using two separate authorities. A run-owned pending policy may require the connecting helper to descend from the run's expected agent process; that ancestry check validates one consumption of the policy and nothing more. Rejoining an established run requires that run's session token. A live run's token outranks a pending policy armed for another run: the connection rejoins its own run at once, and the policy stays for its own helper. When a connection's ancestry matches an established run but it carries neither the run's token nor a pending policy, its `initialize` fails with `expected_pid_without_pending_policy`. The connection never maps to the run or binds a window, its tool requests fail with the same error, and the error names the agent session and the remedy. A bootstrap connection serves tool requests only after RepoPrompt admits one of its `initialize` requests, and never while RepoPrompt is still deciding another. Until then, they fail with an admission-pending error. Bootstrap readiness that lets policy evaluation proceed is not admission. Direct private-endpoint token redemption is unchanged.

App transport lifetime is process-owned from launch through termination. Opening or closing the last window does not start or stop MCP. Window identity is accepted only as an admission selector: public `window_id` binding captures that window's current logical tab as an explicit authoritative context, while hidden `_windowID` captures the same context for one call. Later active-tab changes do not redirect either admitted call or persistent binding. There is no active-tab execution fallback.

Canonical schemas are Swift definitions in `MCPDomainCanonicalToolDefinitions`. Both app and direct registration consume those definitions through `MCPDomainToolRegistry`; there is no legacy service registry, generated resource manifest, live-window recorder, or mixed catalog authority. Provider-built app tools already contain one `MCPAppToolBinder` execution envelope and are projected without wrapping them again; raw shared bindings receive exactly one envelope. Invalid, duplicate, or noncanonical catalogs fail by throwing during startup registration rather than trapping.

Standalone composition uses a `.standalone` registration scope and never creates a synthetic window. Both backends advertise the same canonical `bind_context` schema. It declares `window_id` as an app-backed-only selector: in the app, `list` with `window_id` returns every compose tab of that window, and `bind` with it captures that window's active tab once. In headless mode `bind_context` is global and binds only domain `context_id` or working-directory selectors; `DirectHeadlessGlobalBackend.routeContext` rejects any supplied `window_id`, including `null`, before choosing an operation, so a window selector never changes scope. Direct workspace/read/search/tree/selection/prompt execution delegates to `MCPDomainCanonicalWorkspaceService`. The executable adapter supplies only physical snapshots, mutation persistence, and path resolution, avoiding a second implementation of canonical tool semantics.

App-only physical operations are grouped in `MCPAppPhysicalCapabilityAdapters.Execution`, `.Context`, `.Selection`, `.Files`, and `.Prompt`. The composition root supplies these typed capability families; the retired flat closure dependency bag is not a runtime boundary. The standalone installer reuses `MCPDomainReadToolProvider` and applies both long-running and protected-mutation decorators to every canonical binding. File edits use the shared production apply-edits engine, including operation-ID correlation, revision validation, path fencing, approval, and retry classification.

## Direct transport and child calls

Direct mode installs one MCP SDK `Server` over `MCPStdioServerTransport`; it does not add a second JSON-RPC dispatcher. The transport records one accepted-request/delivered-response hop and distinguishes stdin EOF, truncated EOF, read/poll failure, PPID replacement, broken pipe, write failure, and cancellation. Terminal paths enter bounded host drain before runtime shutdown.

Long-running Agent and Context Builder providers receive an explicit run-scoped carrier. The carrier contains a private Unix endpoint, single-use launch token, verified principal/provider identity, and run ID. The endpoint directory is owner-only, the socket is identity-fenced, and token redemption checks runtime generation, peer PID, expiry, scope, and replay before registering a child connection. App-spawned provider children receive explicit `--backend app`; direct-runtime children use the private run-scoped endpoint and never auto-probe the app.

## State roots and security defaults

The default headless session reads the same canonical application-support and workspace persistence roots as the app of the same build flavor: `RepoPrompt CE` for release and `RepoPrompt CE Debug` for debug, so a debug session never shares state with the release app. It does not derive state from the process current working directory and does not silently create a foreign `Headless/default` profile. This preserves canonical workspace identities, selection persistence, and durable state across app and direct sessions of one flavor.

When every `REPOPROMPT_MCP_WORKING_DIRS` entry is an existing Git worktree of exactly one saved workspace root, direct mode binds that canonical saved workspace and keeps an in-memory canonical-to-physical root map for the process lifetime. `agent_run` existing-worktree selectors replace one physical root in a session-local overlay; nested runs and provider-backed conversations inherit that overlay unless `inherit_worktree=false`. Physical tool execution and root fencing use the selected roots; mappings that carry worktree identity revalidate that Git identity before later use, while workspace documents retain their canonical roots. Direct mode never persists these overlays or a temporary workspace, never creates a worktree, and fails closed on unknown or ambiguous workspace, repository, root, or worktree identity. App-backed routing is unchanged.

`REPOPROMPT_MCP_HEADLESS_PROFILE_DIR` is an explicit isolation boundary for tests and automation. A nondefault `REPOPROMPT_MCP_HEADLESS_PROFILE` requires that directory instead of inventing storage. A debug build rejects an explicit directory that is relative or that resolves to, contains, or lies inside production state, before creating any directory. The same check covers the profile's workspace and event directories and the domain runtime's declared state directories and files. It also ignores a saved custom workspace storage location, and it follows workspace backing paths from catalog, index, or journal metadata only when they resolve inside the profile's `Workspaces` directory. The runtime uses per-workspace journals, revisions, deletion records, and locks only when they resolve inside the profile. Explicit roots may bootstrap a synthetic workspace only inside such an isolated profile. Protected mutations default to deny until the selected persistence policy authorizes the verified principal; long-running provider costs remain decorated and auditable. Direct mode has no AppKit, SwiftUI, window, view-model, live-app, or UI-presentation dependency.

## Validation owners

- Backend-selection tests own the app default, explicit selection, one-shot auto probing, unavailable-app fallback, parser rejection, and no-protocol-bytes probe contract.
- Offline responder tests own the responder's answer to each request and the match of its `initialize` result with a real SDK server's for every supported protocol version. Proxy terminal-record tests own the first-attempt rule. Proxy offline-startup tests drive whole `app`-backend sessions over pipes and a fake bootstrap socket: local answers, late admission, the stdin handoff in both directions, no replay of locally answered calls, a refused or mismatched attachment, the mid-session outage with a quitting app's partial tool list, the helper's `list_changed` and remembered list, and the 60-second grace, end of input, and cancellation. Replay-state tests own which `tools/list` replies the helper remembers, including the rule that a list shrinks only at an attachment. [`docs/testing.md`](../testing.md#live-mcp-helper-without-its-app) has the live checks.
- Domain host tests own admission/drain/generation/watchdog/delivery invariants.
- Canonical catalog tests own all 27 fingerprints, single execution envelopes, fail-closed materialization, and headless `bind_context` semantics.
- Routing tests own exact presentation-to-context capture and rejection when no authoritative context exists.
- Standalone composition tests construct the real runtime without app composition and resolve every canonical tool.
- Direct process tests launch the built executable with no app, exercise canonical state roots and the advertised policy surface, verify denied mutations do not execute, and validate EOF drain.
- Direct worktree-routing tests use real linked Git worktrees and a saved workspace fixture to prove automatic canonical binding, exact existing-worktree selection, coordinator-level detached lifecycle reconciliation, child and provider-conversation inheritance and opt-out, use-time identity revalidation for mappings that carry worktree identity, physical root fencing, stable repository/worktree identities, and zero workspace or worktree-binding persistence. End-to-end `orchestrate` dispatch remains owned by the direct-headless workflow/tool-policy integration boundary rather than this routing fixture.
- Stdio and private-endpoint tests own terminal provenance, bounded broken-pipe behavior, half-close response drain, identity fencing, token redemption, replay, expiry, and foreign-runtime rejection.
- `Scripts/headless_runtime_guardrails.sh` rejects duplicate schema/backend/workspace authorities, flat dependency-bag storage, retired registry/window-tool compatibility types, and MainActor/UI dependencies in the domain runtime.
